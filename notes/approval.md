# 在卡片上批准或拒绝

本文是 FM-14（本项目任务清单里的第 14 项）的设计和实测记录：Claude Code（Anthropic 的 AI 编程助手）要你批准一个操作时，卡片显示要批准的是什么，你在卡片上按一个键就能批准或拒绝。状态怎么从 Mac 到达卡片见 [bridge.md](bridge.md)，hooks（Claude Code 在特定事件发生时自动运行的命令）的实测见 [claude-code.md](claude-code.md)。

## 对照使命

按 [MISSION.md](../MISSION.md) 的“判断一个需求该不该做”逐条回答：

1. **补足的是不是电脑端和手机端都做不好的事？** 是。人不在电脑前时，电脑端的批准弹窗没人看见，Claude Code 就一直停着等。手机端的 Remote Control（用手机远程操作 Mac 上的 Claude Code）能批准，但要先掏出手机、解锁、打开 App。卡片补的是 MISSION.md 说的“按一个键就能答”。
2. **看一眼就能懂吗？** 能。屏幕写着“等你批准”、工具名（比如 `Bash`）和命令的前几行，底部写着哪个键批准、哪个键拒绝。
3. **按一两个键就能完成吗？** 能。长按右侧最上面的键批准，按一下右侧最下面的键拒绝。
4. **人不在电脑前、不想掏手机时还有用吗？** 有用，这正是它的使用场景。

项目负责人 2026-10-16 决定不要“离开开关”（G18）：每次要批准时，卡片和终端同时能答，哪边先答算哪边。

## 整体流程

```text
+-------------+  [1]   +-------------+  [2]   +-------------+
| Claude Code | -----> | bridge hook | -----> | bridge app  |
|   session   | <----- |   (waits)   | <----- |  resident   |
+-------------+  [6]   +-------------+  [5]   +-+----+------+
                                                ^    |
                                            [4] |    | [3]
                                                |    v
                                              +-+----+------+
                                              |    card     |
                                              +-------------+
```

1. Claude Code 要你批准一个操作时，同时弹出终端里的批准弹窗、运行 `PermissionRequest` hook。hook 就是桥接程序的 `hook` 模式。
2. 对 `PermissionRequest`，`hook` 模式不马上退出：它把请求交给常驻的桥接程序，然后一直等回答。
3. 桥接程序把最早的那个请求写给卡片，卡片显示要批准的内容。
4. 你在卡片上按键，卡片把“批准”或“拒绝”连同这个请求的编号发回桥接程序。
5. 桥接程序把回答交给正在等的 `hook` 进程。
6. `hook` 进程按官方格式在标准输出写出回答，Claude Code 照着执行，终端里的弹窗随之消失。

## 哪边先答算哪边

| 情况 | 桥接程序怎么知道 | 之后 |
| --- | --- | --- |
| 卡片上批准 | 卡片发回“批准” | hook 回答 allow，命令运行；卡片撤掉提示，显示干活中 |
| 卡片上拒绝 | 卡片发回“拒绝” | hook 回答 deny，并告诉 Claude 是在卡片上拒绝的；卡片撤掉提示，显示干活中，Claude 接着处理 |
| 终端里批准 | 同一个操作的 `PostToolUse` 或 `PostToolUseFailure`（工具用完 / 运行失败）到达 | hook 不回答直接退出；卡片撤掉提示 |
| 终端里拒绝（按 Esc 或选“3. No”） | Claude Code 马上结束正在等的 hook 进程，hook 和桥接程序之间的连接断开 | 卡片撤掉提示，这个会话改成空闲（G23） |
| hook 等到自己的上限（默认 590 秒） | hook 告诉桥接程序它不等了 | 卡片撤掉提示，仍显示等你批准，因为终端里的弹窗还在 |
| 用户发了下一条指令、这一轮结束或会话结束 | `UserPromptSubmit`、`Stop`、`StopFailure`、`SessionEnd` | 这个会话所有还在等的 hook 不回答直接退出 |

几条规则的理由：

- **终端里批准时，提示要等工具用完才撤掉**：Claude Code 在终端批准后不结束 hook 进程，也不发任何事件，直到工具用完才有 `PostToolUse`（[claude-code.md](claude-code.md) 的结论第 3 条）。所以一个要跑很久的命令在终端批准后，卡片上的提示会一直留到命令跑完。这时在卡片上再答，Claude Code 会忽略（FM-8 实测过迟到的拒绝不起作用）。
- **终端里拒绝时为什么能知道**：这是 FM-14 实测出来的（见“实测结果”第 1 条），官方文档没写。将来 Claude Code 不再结束 hook 进程时，卡片退回 FM-13 的表现：显示等你批准，直到下一条指令。
- **hook 为什么要有自己的上限**：Claude Code 给 hook 设了超时（官方默认 600 秒），到时会结束它。hook 自己在 590 秒时先退出，桥接程序就能分清“你在终端拒绝了”和“只是等太久”。
- **卡片发回的回答带请求编号**：你按键的那一刻，卡片上的提示可能刚好换成了下一个请求。桥接程序只接受和当前显示的请求编号相同的回答，其他的丢掉。

## 卡片怎么显示

有请求在等时，卡片换成批准画面：

- 最上面一行：“等你批准”，右上角是“第几个 / 一共几个”，比如 `1/2`。
- 第二行：工具名，比如 `Bash`、`Write`。太长时截断，用 `…` 结尾，比如 `mcp__claude-in-chrome_…`。
- 中间：要批准的内容，最多 7 行，超出的用 `…` 结尾。Bash 显示命令；改文件的工具显示文件路径；网页工具显示网址；其他工具只显示工具名。中文等非英文字符显示成 `?`，因为卡片里只放了英文字母、数字和符号的字形。
- 最下面两行：`长按右侧最上面的键 批准`、`按右侧最下面的键 拒绝`。

按键之后，卡片显示“已批准”或“已拒绝”，直到桥接程序撤掉这个请求或换成下一个。

## 按键

卡片左侧一个键是电源，右侧从上到下三个键在固件里叫 `ok`、`up`、`down`。屏幕提示只说键的位置，不说“确认键”“下键”：第一次配对时屏幕写的是“按确认键”，用户以为最下面那个是确认键，按下去就把配对取消了（G24）。

- **长按右侧最上面的键（0.7 秒）批准**：批准会运行命令，长按可以防止碰一下就批准。
- **长按批准的是按下那一刻屏幕上的那条请求**：按住期间请求换了（比如终端先答了它，屏幕换成下一条），或者按下时还没有请求、按住期间才出现，到 0.7 秒时都不批准。要批准屏幕上新的那条，松开再长按一次。
- **按一下右侧最下面的键拒绝**：拒绝不会造成损失，所以不用长按。
- 右侧中间的键在批准画面里不起作用。
- 配对画面里，按键只用来配对，不会批准或拒绝请求。
- 没有请求在等时，按键和以前一样，只从串口报出来。

## 蓝牙配对加密

卡片按键能批准命令，所以只有你自己的 Mac 能连卡片、收卡片的回答。卡片的三个特征值（蓝牙里用来读写数据的小格子）都要求连接先完成配对加密：

- **配对方式**：LE Secure Connections（蓝牙 4.2 起的安全配对方式），要求防中间人（MITM，有人冒充两边中的一边偷听或改数据），并且绑定，也就是两边记住彼此，以后连上自动加密。
- **第一次配对**：桥接程序第一次连上卡片、写入状态时，macOS 弹出蓝牙配对对话框，上面有六位数字；卡片同时换成蓝色的“蓝牙配对”画面，显示同一串数字（这种方式叫数字比较）。两边数字相同时，在 Mac 上点“连接”，再按卡片右侧最上面的键；不同就按右侧最下面的键取消。
- **配对失败或取消之后**：macOS 不会在同一条连接上再试一次配对，之后每次写入都马上失败（错误码 5，“认证不够”）。要退出桥接程序再启动，新的连接会重新弹出配对对话框（实测见“实测结果”第 2 条）。
- **绑定信息**：卡片存在 Flash 的 NVS 区（ESP-IDF 存小块数据的地方），重新烧录程序不会清掉。串口命令 `ble unpair` 清掉卡片上的全部绑定；清掉后 Mac 上也要在“系统设置 → 蓝牙”里忽略这张卡片，再重新配对。

## 蓝牙协议

服务编号不变（`6d2f1001-6b0e-4a8e-9a4b-46756e4d6564`），多了两个特征值。三个特征值都要求加密且防中间人的连接。

| 名字 | 编号 | 怎么用 |
| --- | --- | --- |
| STATE | `6d2f1002-…` | 同 [bridge.md](bridge.md) |
| PROMPT | `6d2f1003-…` | Mac 写入当前要显示的请求，格式是 `<编号>\t<第几个>\t<一共几个>\t<工具名>\t<内容>`，编号和两个数都是十进制数字，工具名最多 31 字节，内容最多 240 字节；写入空内容表示没有请求在等。格式不对时拒绝，屏幕不变 |
| DECISION | `6d2f1004-…` | 卡片在按键后通知 Mac：`<编号> allow` 或 `<编号> deny`。Mac 连上后订阅它 |

卡片从 USB 串口报这些行，测试靠它们读回卡片做了什么：

- `PROMPT <编号> <第几个>/<一共几个> <工具名>`：开始显示一个请求；`PROMPT none`：没有请求了。
- `DECISION <编号> allow|deny`：按键后发出的回答。
- `BLE sec encrypted=<0|1> authenticated=<0|1> bonded=<0|1> key_size=<字节>`：连接的加密状态变了。
- `PAIR passkey <六位数>`、`PAIR numcmp <六位数>`、`PAIR done status=<码>`：配对过程。

`info` 多了 `prompt=<编号|none>`、`sec=<encrypted,authenticated,bonded 中已满足的，用逗号隔开，或 none>`。新的串口命令：

| 命令 | 作用 |
| --- | --- |
| `key <ok\|up\|down> <press\|long\|hold <毫秒>>` | 模拟一次按键：`press` 是按下再松开，`long` 是按住超过 0.7 秒再松开，`hold <毫秒>` 是按住指定的毫秒数（1–20000）再松开，按住满 0.7 秒时和真按键一样报 `KEY long`。走和真按键相同的处理，测试用它代替人按键 |
| `ble unpair` | 清掉卡片上的全部绑定 |

## hook 模式的变化

- `PermissionRequest` 的 `hook` 进程会一直等，直到桥接程序给出回答、撤掉请求，或者到了 `--wait-limit <秒>`（默认 590）。所以 `~/.claude/settings.json` 里这一个事件的 `timeout` 要设成 600。
- **连不上就不等**：hook 连接桥接程序最多等 1 秒，桥接程序确认收到请求最多等 2 秒；任一步没成，hook 不回答直接退出，退出码 0，终端照常问你。
- 回答的格式按官方文档：批准时写 `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`，拒绝时 `behavior` 是 `deny`，并带一句 `message` 告诉 Claude 是在卡片上拒绝的。不回答时什么都不写。
- **传给桥接程序的内容多了一项**：只有 `PermissionRequest` 会多传一段 `summary`（要显示在卡片上的内容，按上面“卡片怎么显示”的规则从工具参数里取，最多 240 字节）。它只经过桥接程序的内存和加密的蓝牙到达卡片，不写进桥接程序的记录。其他事件仍按 [bridge.md](bridge.md) 的“只传需要的几项”。

## 实测结果

1. **终端里拒绝时 hook 进程会被结束**：让 `PermissionRequest` hook 等 8 秒后回答 allow，在第 2 秒时于终端拒绝。按 Esc 那次 0.11 秒后、选“3. No”那次 0.03 秒后，hook 进程都收到了 SIGTERM（请程序结束的信号），那个迟到的 allow 没有发出，命令也没有运行（`artifacts/fm14-late-allow-probe-20261016-232012/`，里面有探测脚本）。
2. **第一次配对**：第一次时屏幕写“按确认键配对”，用户按了右侧最下面的键，配对被取消；之后桥接程序的写入先等了约 31 秒报错误码 15（“加密不够”），以后每次马上报错误码 5（`artifacts/fm14-pairing-20261017-000303/`，有屏幕截图）。提示改成按位置说键之后重启桥接程序，第二次配对成功：卡片报 `PAIR numcmp`、`PAIR confirm accept=1`、`BLE sec encrypted=1 authenticated=1 bonded=1 key_size=16`、`PAIR done status=0`（`artifacts/fm14-pairing-20261017-001003/`）。
3. **终端里拒绝后卡片撤掉提示的时间**：按 Esc 那次 0.159 秒、选“3. No”那次 0.104 秒，桥接程序记录的关闭方式都是 `hung_up`（hook 被结束，连接断开），命令都没运行，撤掉后再在卡片上按键没有发出回答（`artifacts/fm14-real-20261017-001236/approval/test_terminal_rejection/`）。
4. **真人按键**：用户先短按了一下右侧最上面的键，卡片没有当成批准；接着长按它，卡片发出 `DECISION 1 allow`，命令运行；第二个请求时按一下右侧最下面的键，卡片发出 `DECISION 2 deny`，命令没运行（`artifacts/fm14-person-20261017-002413/`）。
5. **按键任务的栈**：原来按键任务的栈是 3072 字节，FM-13 的栈测试没走按键路径；加上批准以后，按键事件处理完只剩 980 字节（`artifacts/fm14-before-20261016-234223/`）。改成 4096 字节，并让测试注入的按键也在按键任务里处理，之后按键任务剩 1968 字节。
6. **长按批准绑定按下时的请求**（代码审查发现）：修复前，按住期间终端答了请求 1、屏幕换成请求 2，到 0.7 秒时卡片批准了请求 2；按下时没有请求、按住期间请求 1 才出现，卡片也批准了它（`artifacts/fm14-binding-before-20261017-005719/`）。修复后两种情况都不批准，松开再长按才批准屏幕上那条（`artifacts/fm14-fixes-after-20261017-010106/`）。
7. **长工具名**：修复前 `mcp__claude-in-chrome__javascri` 在屏幕右边距里画出 45 个像素，字被屏幕边缘切断（`artifacts/fm14-fit-before-device-20261017-010031/`）；修复后截断在右边距以内，用 `…` 结尾（`artifacts/fm14-fixes-after-20261017-010106/`）。
8. **订阅回答也要求加密**：Mac 要先订阅 DECISION（告诉卡片“有回答就通知我”）才能收到回答。以前订阅这一步不要求加密；卡片发回答前本来就检查连接已加密，所以没加密的连接收不到回答。现在订阅本身也要求加密且防中间人，改后批准和拒绝的测试照常通过。这一项没有修复前失败的测试：测试用的 Mac 已和卡片绑定，连上就自动加密，手头没有一台没配对的设备去试订阅。

## 还没做的

代码审查（2026-10-17）发现、要改桥接程序的三处，留到下一次重新编译桥接程序时一起改，因为每次重新编译后 macOS 都要你再点一次允许蓝牙：

- **一模一样的两条命令**：卡片批准一条命令后，Claude Code 运行它并报 `PostToolUse`。如果这时还有一条一模一样的命令在等批准，桥接程序会把那条也当成“终端已经答了”，撤掉它在卡片上的提示，你只能在终端答它。不会批准错命令。
- **hook 到上限放弃的同一刻卡片批准了**：hook 等满 590 秒时发出“放弃”就退出。如果卡片的批准恰好在这一刻送到，批准就丢了：卡片显示“已批准”，命令没运行，终端照常问你。
- **两处安全检查还没有测试**：卡片发来一个已经不在等的编号时，桥接程序不理它；没配对的设备连上卡片读写不了。

- **两张卡片**：桥接程序仍然连第一张搜到的卡片，见 [bridge.md](bridge.md) 的“还没做的”。配对加密以后，没配对过的卡片连上也读写不了，但桥接程序不会自己换一张。
