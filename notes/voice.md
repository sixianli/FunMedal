# 按住说话

本文是 FM-15（本项目任务清单里的第 15 项）的设计和实测记录：按住卡片上的一个键说一句话，松开后这句话变成文字，送进正在运行的 Claude Code（Anthropic 的 AI 编程助手）会话，就像你在终端里打了这句话。批准和拒绝见 [approval.md](approval.md)，桥接程序（Mac 上把 Claude Code 和卡片连起来的程序）见 [bridge.md](bridge.md)。

## 对照使命

按 [MISSION.md](../MISSION.md) 的“判断一个需求该不该做”逐条回答：

1. **补足的是不是电脑端和手机端都做不好的事？** 是。人不在电脑前时，电脑端没法给 Claude 下新指令。手机端的 Remote Control（用手机远程操作 Mac 上的 Claude Code）能打字，但要掏出手机、解锁、打开 App、找到会话再打字。卡片补的是 MISSION.md 说的“按住说一句短指令”：比如 Claude 答完一轮（卡片显示“完成了”），你在屋里另一头按住键说“接着把测试跑一遍”。
2. **看一眼就能懂吗？** 能。按住时屏幕写“在听”，松开后写“转文字中”，送进去以后显示送进去的那句话。
3. **按一两个键或说一句话就能完成吗？** 能。按住一个键、说一句、松开。
4. **人不在电脑前、不想掏手机时还有用吗？** 有用，这正是它的使用场景。

## 整体流程

```text
           [1]            [2]            [3]             [4]
+--------+     +--------+     +--------+     +---------+     +-------------+
|  card  | --> | bridge | --> | speech | --> | channel | --> | Claude Code |
+--------+     +---+----+     +--------+     +---------+     +-------------+
    ^              |
    |     [5]      |
    +--------------+
```

1. 按住键时，卡片从麦克风录音，压缩后边录边用加密的蓝牙发给 Mac 上的桥接程序。
2. 桥接程序把收到的声音交给 macOS 自带的离线语音识别（`SFSpeechRecognizer`，Apple 的语音转文字接口，`requiresOnDeviceRecognition` 设为真，声音不出这台 Mac）。
3. 松开键后，识别出的文字交给对应会话的频道服务器。频道服务器是 Claude Code 为每个会话启动的一个子程序，也是桥接程序的一种模式（`channel` 模式）。
4. 频道服务器用 Channels（Claude Code 的“频道”功能：一个 MCP 服务器往运行中的会话推消息）把这句话推进会话，Claude 把它当成你的一条指令。
5. 桥接程序把结果告诉卡片：送进去的那句话，或者没送成的原因。

## 按键

- **按住右侧中间的键说话，松开发送**。不用最上面的键，因为批准画面里长按最上面的键是批准，同一个动作在两个画面里意思不同，容易把“想说话”按成“批准”。中间的键在批准画面里本来不起作用，所以在批准画面里也能按住说话，比如说“别删那个目录，先备份”。
- **按住不到 0.5 秒就松开**：当成误触，不录也不发。
- **最长 15 秒**：按住超过 15 秒自动停止并发送，因为这里只说短指令（MISSION.md）。
- **配对画面里不能说话**：配对时只认最上面和最下面两个键。

## 卡片怎么显示

| 什么时候 | 屏幕 |
| --- | --- |
| 按住时 | 大字“在听”，下面一行“松开就发送” |
| 松开后，等 Mac 转文字 | 大字“转文字中” |
| 送进去了 | 大字“已发送”，下面是送进去的那句话的图片（最多 5 行，见下面） |
| 没送成 | 大字“没发出去”，下面一行原因：没听清、没有能接收的会话、Mac 没有语音识别权限、没连上 Mac |

结果显示 4 秒后回到原来的画面（宠物画面或批准画面）。转文字超过 15 秒没有结果，卡片也显示“没发出去”，原因是“Mac 没有回音”。

**送进去的那句话怎么显示**：卡片里的点阵字体只有屏幕固定文字用到的几十个汉字，识别出来的话里大多数汉字都没有。所以由 Mac 用系统字体把这句话画成一张 220×100 像素的黑白图片（每像素 1 位，每行补齐到整字节，共 2800 字节），通过蓝牙发给卡片，卡片照着图片画。这样你能看到送进去的到底是哪句话：识别错了，Claude 就会照着错的话去做，你可以马上回电脑纠正。图片只在 Mac 上用本机字体临时画出，不往卡片里放字体。

## 声音怎么从卡片到 Mac

- **录音**：卡片上的音频芯片 ES8311（把麦克风的声音变成数字信号的芯片，见 [hardware.md](hardware.md)）通过 I2S（芯片之间传声音数据的接口）给主控每秒 16000 个采样，每个采样 16 位，单声道。
- **压缩**：卡片把每个采样压成 4 位的 IMA ADPCM（一种简单的音频压缩，只记录和上一个采样的差），每秒 8000 字节，约 64 kbps，是 FM-11 实测最慢蓝牙速度的 21%（[ble-link.md](ble-link.md)）。
- **分包**：每 20 毫秒（320 个采样）一个包。每个包带上压缩器当时的状态，丢了一个包，后面的包照样能解开，Mac 把丢的那 20 毫秒补成静音。

AUDIO 特征值（蓝牙里用来读写数据的小格子）`6d2f1005-…`，卡片用通知发给 Mac，要求加密且防中间人的连接。每个包的第一个字节是类型，数字一律是小端（低位字节在前）：

| 类型 | 内容 | 什么时候发 |
| --- | --- | --- |
| `0x01` 开始 | 第 2 字节：这段话的编号（每段加一，0–255 循环） | 按住满 0.5 秒时 |
| `0x02` 声音 | 第 2 字节：编号；第 3–4 字节：包序号，从 0 开始；第 5–6 字节：这个包第一个采样之前的预测值；第 7 字节：步长序号；之后 160 字节：320 个 4 位采样，每字节先低 4 位后高 4 位 | 录音期间每 20 毫秒 |
| `0x03` 结束 | 第 2 字节：编号；第 3–4 字节：一共发了几个声音包；第 5 字节：为什么结束（0 松开，1 到了 15 秒） | 松开或到 15 秒时 |

VOICE 特征值 `6d2f1006-…`，Mac 写给卡片这段话的结果，格式是 `<编号>\t<结果>`。`<结果>` 是 `sent`（送进去了）、`empty`（没听清）、`no_session`（没有能接收的会话）、`denied`（这台 Mac 不能做离线语音识别：没有授权，或者这种语言没有离线识别）之一。卡片自己还会得出两种结果，不经过 Mac：`offline`（按下时或录完时没连着 Mac）、`timeout`（录完 15 秒内 Mac 没回结果）。

VOICE_IMAGE 特征值 `6d2f1007-…`，Mac 在写 `sent` 结果之前，分几次写入那句话的图片：每次的第 1 字节是这段话的编号，第 2–3 字节是这次数据在图片里的起始位置，之后是图片数据。每次最多写 512 字节，一张图分 6 次写完。图片按行存，每行 220 像素占 28 字节（最后 4 位不用），一共 100 行、2800 字节；每个字节的最高位是这 8 个像素里最左边的那个，1 表示有字。几次写入必须按顺序接上，起始位置是 0 的那次重新开始一张图。卡片收齐同一编号的 2800 字节后，收到 `sent` 时显示这张图；没收齐就只显示“已发送”。

卡片从 USB 串口报这些行，测试靠它们读回卡片做了什么：`VOICE start <编号>`、`VOICE end <编号> packets=<包数> dropped=<没发出去的包数> reason=<release|limit|offline>`、`VOICE result <编号> <结果>`、`VOICE short`（不到 0.5 秒，丢掉）、`VOICE unavailable <原因>`（开机时音频芯片没初始化成功，按住说话不可用）。

测试用的串口命令：

| 命令 | 作用 |
| --- | --- |
| `mic <包数 1–500> [增益 0–7]` | 不经过蓝牙，直接录指定包数的声音，每包一行 `MIC <序号> <十六进制数据>`，最后一行 `OK mic packets= gain= rms= other_rms= peak=`：`rms` 是用到的那个声道的均方根（声音大小的一种量法），`other_rms` 是另一个声道，`peak` 是最大值。增益每加 1，麦克风放大 6 分贝，默认 4 |

`info` 多了 `voice=<none|listening|transcribing|result>` 和 `mic=<ready|off>`，`stacks` 多了 `voice`（录音任务的栈还剩多少字节）。

## 送进哪个会话

同一台 Mac 上可能同时开着几个 Claude Code 会话。2026-10-17 实测（`artifacts/fm15-session-map-probe-20261017-004113/`）：

- Claude Code 启动的频道服务器和 hook 进程，父进程都是同一个 `claude` 进程。
- 频道服务器的环境变量 `CLAUDE_CODE_SESSION_ID` 和 hook 收到的 `session_id` 相同。这个变量官方文档没写。

所以每条 hook 消息都带上 `claude_pid`（它属于哪个 `claude` 进程）：hook 进程的环境变量里有 `CLAUDE_PID`（官方文档没写）时用它，没有或者不是数字时用自己的父进程号。频道服务器连上桥接程序时报自己的父进程号。桥接程序据此知道每个频道属于哪个会话。不用 `CLAUDE_CODE_SESSION_ID`，是因为用户在会话里输入 `/clear` 后会话编号会换，而频道服务器还是原来那个进程。

送给谁：桥接程序记下每个 `claude` 进程最近一次“和人有关”的时间：会话开始（`SessionStart`）、你发了指令（`UserPromptSubmit`）、要你批准（`PermissionRequest`）、答完一轮或出错（`Stop`、`StopFailure`），以及它的频道刚连上。在连着的频道里，选这个时间最近的那个。工具开始和用完（`PreToolUse`、`PostToolUse`）不算：比如会话 A 刚显示“完成了”，你对它说“接着把测试跑一遍”，这时会话 B 正在跑命令，B 的工具事件不会把这句话抢走。没有任何频道连着时，卡片显示“没有能接收的会话”。

## Mac 端

- **桥接程序**（常驻的 `serve` 模式）：订阅 AUDIO，按编号收一段话，解压，边收边交给语音识别。中间丢了包，就补上同样长的静音。收到“结束”包后：
  1. 这台 Mac 不能做离线识别，回 `denied`。
  2. 没有频道连着，马上回 `no_session`，不等识别。
  3. 否则等最终结果，最多 10 秒，到时用已经识别出的部分。识别出的是空的，回 `empty`。
  4. 有文字时，把它交给最近有动静的那个频道，再把它画成图片写给卡片，最后写 `sent`。

  识别用的语言默认是简体中文（`zh-CN`），启动时加 `--voice-locale <语言>` 可以换。
- **频道服务器**（`channel` 模式）：Claude Code 按 MCP 配置启动它，用标准输入输出交换 JSON-RPC（MCP 用的一种“请求—回答”消息格式）消息。它回答 `initialize` 时声明协议版本 `2025-06-18` 和 `claude/channel` 能力，不实现 `server/discover`（理由见 [claude-code.md](claude-code.md) 的“Channels”），`ping` 回空结果，其他请求回“不支持这个方法”（错误码 -32601）。收到 `notifications/initialized` 后，它才连桥接程序的套接字、报自己的父进程号；连不上或者连接断了，每 2 秒重试一次，所以桥接程序晚启动或者重启都没关系。之后它一直等桥接程序送来的文字，收到一句就用 `notifications/claude/channel` 推进会话。它不碰蓝牙和语音识别，所以和 `hook` 模式一样可以由 Claude Code 直接运行。
- **桥接程序和频道服务器之间**：频道服务器发 `{"op":"listen","claude_pid":<进程号>}`，桥接程序回 `{"ok":true}`，之后这条连接一直开着；桥接程序每送一句发一行 `{"clip":<编号>,"say":"<文字>"}`。频道服务器退出时连接断开，桥接程序就不再往它送。
- **图片怎么画**：用系统界面字体（中文是苹方）17 像素，行高固定 20 像素，所以最多 5 行，每行大约 12 个汉字。超过 5 行时，最后一行末尾换成“…”。灰度低于一半的像素算有字。
- **`status` 多了几项**：`channels`（连着的频道各属于哪个 `claude` 进程）、`speech`（语音识别授权：`authorized`、`denied`、`restricted`、`not_determined`）、`voice`（已经回过几段话的结果）。
- **记录里多了几种**：`listen` / `unlisten`（频道连上 / 断开，带进程号）、`voice_start`（带编号和授权状态）、`voice_end`（带包数、补成静音的包数、结束原因）、`voice_result`（带结果、文字的字数、图片里有字的像素数、送给了哪个进程）、`voice_bad`（收到格式不对的包）。
- **权限**：第一次运行 `speech-access` 模式时，macOS 问是否允许语音识别，选允许。没先运行它就按住说话时，桥接程序在这一段话开始时才请 macOS 弹出授权框，这一段话本身会显示“Mac 没有语音识别权限”，允许之后的下一段话才能用。桥接程序每次改代码重新编译后，macOS 都会把它当成新程序，蓝牙和语音识别都要再允许一次（见 [bridge.md](bridge.md) 的“怎么配置”）。
- **隐私**：声音只在内存里，不存文件。桥接程序的记录只记每段话的编号、包数、文字长度和结果，不记文字本身。

## 怎么配置

1. 让 macOS 允许语音识别（只需一次）：

   ```bash
   open -W mac/bridge/build/FunMedalBridge.app --args speech-access
   ```

2. 把频道服务器写进一个单独的 MCP 配置文件，比如 `~/.config/funmedal/mcp.json`，`<仓库路径>` 换成 FunMedal 仓库的绝对路径：

   ```json
   {"mcpServers": {"funmedal": {"command": "<仓库路径>/mac/bridge/build/FunMedalBridge.app/Contents/MacOS/funmedal-bridge",
                                "args": ["channel"]}}}
   ```

3. 每次要用按住说话时，用这个文件和开发频道参数一起启动 Claude Code，并在警告里选“1. I am using this for local development”。FM-8 实测过开发频道参数是加载自己写的频道的唯一办法：

   ```bash
   claude --mcp-config ~/.config/funmedal/mcp.json --dangerously-load-development-channels server:funmedal
   ```

   **不要把它写进 `~/.claude.json` 或项目的 `.mcp.json`**：那样不带开发频道参数启动的会话也会启动频道服务器，它照样向桥接程序登记。Claude Code 发来的 `initialize` 里看不出这个会话有没有开频道（FM-8 的记录），桥接程序可能把话送给这样的会话；按官方文档，这种会话不接收频道推来的消息，卡片却显示“已发送”。这一点没有在本机实测。

## 测试要覆盖的情况

测试在 [tests/test_voice.py](../tests/test_voice.py)，压缩和解压在 [tests/host/test_voice_codec.c](../tests/host/test_voice_codec.c)。要朗读的测试固定用 Mac 自带的扬声器播放（`say -a`，找名字以 `Speakers` 结尾或含 `Built-in` 的设备），不跟系统的默认输出走：默认输出是耳机时，卡片听不到。别的设备可以用环境变量 `FM_SAY_DEVICE` 指定。“测试自己当频道”指测试程序连上桥接程序的套接字、发 `listen`，收桥接程序送来的文字。

| 编号 | 情况 | 期望 | 怎么测 |
| --- | --- | --- | --- |
| 1 | 压缩和解压 | 卡片的压缩代码压出来的数据，解开后和原始声音的差距在 ADPCM 正常范围内；丢一个包后面照样能解；结果和图片的格式不对时拒绝 | 在 Mac 上编译固件的压缩代码直接测 |
| 2 | 麦克风真的在录 | 增益 0 和 7 各录 100 个包：序号连续、每包 167 字节、约 2 秒收齐；Mac 解压后算出的声音大小和卡片自己算的一致；增益 7 的声音大小是增益 0 的 2 倍以上 | 卡片串口 `mic`，录的是房间里的环境声 |
| 3 | 按住说话走一遍 | Mac 用 `say` 朗读“把测试跑一遍”，卡片按住中间的键录下来；文字含“测试”，只送给最近需要你的那个会话的频道，另一个会话之后跑工具也不会抢走；卡片显示“已发送”，图片里有字的像素数和桥接程序画的一样多；桥接程序的记录里没有这句话 | 串口注入按住，真实蓝牙、真实语音识别，测试自己当两个频道，用带 `CLAUDE_PID` 的 hook 消息决定哪个最近有动静 |
| 4 | 送进真实会话 | 频道服务器把文字推进真实 Claude Code 会话，Claude 照着做 | 真实会话，带开发频道参数启动（还没写，见“还没做的”） |
| 5 | 按住太短 | 不到 0.5 秒松开，什么都不发 | 串口注入 |
| 6 | 按住超过 15 秒 | 15 秒时自动结束，正好 750 个包，结束原因是 `limit` | 串口注入 |
| 7 | 没有频道连着 | 卡片 1 秒内显示“没有能接收的会话” | 不连频道 |
| 8 | 什么都没说 | 卡片显示“没听清”，频道什么都没收到 | 测试自己当频道，不放声音 |
| 9 | 批准画面里说话 | 松开后卡片还显示“转文字中”或结果时，长按最上面的键不批准；结果显示完回到批准画面，请求还在，批准照样生效。按住中间的键时不能同时按最上面的键：3 个键共用一根电压引脚，同时按读出的是另一个电压 | 模拟 hook 事件 + 串口注入 |
| 10 | 声音占用卡片资源 | 录音期间按键任务间隔不超过 30 毫秒；录完各任务的栈至少剩 1024 字节 | `info` 的 `key_gap_ms`、`stacks` |
| 11 | 没连着 Mac | 按住时马上显示“没连上 Mac”，不录也不发 | 不启动桥接程序 |
| 12 | 频道服务器的握手和转发 | 回答 `initialize` 的内容对；`notifications/initialized` 之前不连桥接程序；之后报自己的父进程号，收到的文字原样推进会话；`ping`、不支持的方法、通知都按规则回或不回；标准输入关掉后 2 秒内退出 | 测试自己当 Claude Code 和桥接程序 |
| 13 | 桥接程序晚启动或重启 | 频道服务器照常回答 Claude Code；桥接程序出现或重启后 3 秒内重新连上 | 测试自己当桥接程序，先不监听，再断开一次 |
| 14 | hook 报的进程号 | 有 `CLAUDE_PID` 时报它；没有或者不是数字时报自己的父进程号 | 测试自己当桥接程序 |

## 实测结果

卡片这一侧，2026-10-17，`artifacts/fm15-card-20261017-012338/`：
