# Mac 桥接程序和卡片的状态显示

本文是 FM-13（本项目任务清单里的第 13 项）的设计和实测记录：Claude Code（Anthropic 的 AI 编程助手）的会话状态怎样从 Mac 到达卡片屏幕。2026-10-24 起（SC-16，状态卡片长任务的第 16 项），卡片上的批准和按住说话已经拿掉，本文写的是拿掉以后的做法；下文带日期的实测记录照原样保留，里面提到批准和语音的地方是当时的情况。卡片上画什么见 [firmware.md](firmware.md)，蓝牙速度见 [ble-link.md](ble-link.md)，hooks（Claude Code 在特定事件发生时自动运行的命令）的实测见 [claude-code.md](claude-code.md)。

## 对照使命

按 [MISSION.md](../MISSION.md) 的“判断一个需求该不该做”逐条回答：

1. **补足的是不是电脑端和手机端都做不好的事？** 是。电脑端只有坐在 Mac 前、窗口没被挡住时才看得到 Claude Code 在干什么。手机端的 Remote Control（用手机远程操作 Mac 上的 Claude Code）要先解锁手机、打开 App 才看得到。卡片一直亮着，补的是 MISSION.md 说的第一件事：“看一眼就知道状态”。
2. **看一眼就能懂吗？** 能。屏幕只有一个像素小人和两三个字（空闲、干活中、等你批准、完成了、出错了），每种状态的背景颜色不同。（这是当时的画面；2026-10-25 起换成一行一个会话的任务板，见 [firmware.md](firmware.md) 的“现在能做什么”）
3. **按一两个键或说一句话就能完成吗？** 这一项只显示，不用按键。要你批准时到电脑上答。
4. **人不在电脑前、不想掏手机时还有用吗？** 有用。这正是它的使用场景：人在别处，抬头看一眼卡片，就知道该不该回电脑。

## 整体结构

```text
+-------------+   [1]    +-------------+   [2]    +-------------+
| Claude Code | -------> | bridge hook | -------> | bridge app  |
|   session   |  stdin   |   process   |  socket  |  resident   |
+-------------+          +-------------+          +------+------+
                                                         |
                                                         | [3] BLE write
                                                         v
                                                  +-------------+
                                                  |    card     |
                                                  +------+------+
                                                         |
                                                         | [4] USB serial
                                                         v
                                                  +-------------+
                                                  |  test only  |
                                                  +-------------+
```

1. Claude Code 每发生一个事件（比如用户发了指令、要用户批准、答完一轮），就运行一次配置好的 hook 命令，把事件内容用 JSON（一种常见的文本数据格式）写进它的标准输入。这个命令就是桥接程序的 `hook` 模式。
2. `hook` 模式只摘出需要的几项，通过 Unix 套接字（同一台电脑上两个程序互相传数据的通道，表现为一个文件路径）交给常驻的桥接程序，然后马上退出。
3. 常驻的桥接程序记着每个会话的状态，排成一张最多 6 行的会话表。表变了就用 BLE（低功耗蓝牙）写给卡片。
4. 卡片的 USB 串口只在测试时用：测试从这里读回卡片收到了什么、显示了什么，平时不需要接 USB。

桥接程序是一个 Swift 写的 Mac 应用包（`.app`），没有窗口，也不在程序坞里显示。它必须由 `open`（macOS 打开应用的命令）启动，否则 macOS 会因为它用蓝牙而把它结束（见 [ble-link.md](ble-link.md) 第 4 条影响）。`hook` 模式不碰蓝牙，所以可以由 Claude Code 直接运行。以前给按住说话用的 `listen` 模式、`said` 和 `speech-access` 命令，2026-10-24 删掉了。OB-11 起还有 `doctor` 命令，用来排查装好后哪里不对，见下文“doctor 自检”。

## 卡片怎么收状态

卡片开一个蓝牙服务，编号 `6d2f1001-6b0e-4a8e-9a4b-46756e4d6564`，对外广播的名字是 `FunMedal`。2026-10-24（状态卡片实施计划 Task 2）起服务里只有两个特征值（蓝牙里用来读写数据的小格子），都要求配对加密，见 [approval.md](approval.md) 的“实测结果”。以前的 STATE（`6d2f1002-…`）和批准、语音用的五个（`6d2f1003-…` 到 `6d2f1007-…`）一起删了：

| 名字 | 编号 | 怎么用 |
| --- | --- | --- |
| VERSION | `6d2f1008-…` | 连接协议版本号，见下文“先核对版本” |
| ROWS | `6d2f1009-…` | Mac 写入整张会话表（下面叫“一帧”），要卡片确认收到（“有响应写入”）。只能写，不能读 |

一帧是二进制，一次写完、不分包：

```text
offset  size  content
0       1     format, always 1
1       1     total sessions (0 = no session)
2       1     shown rows = min(total, 6)
3       1     flags: bit0 = heartbeat, other bits 0
4...    each  row id (1-255) + state + minutes (2, little endian) + name length (<= 32) + name (UTF-8)
```

- **状态字节**：低 4 位是 1 等你、2 出错、3 在跑、4 答完了；最高位是“新进入”，表示这一行这一帧刚变成等你或出错，卡片只靠这一位决定要不要提醒。只有等你和出错能带这一位。
- **分钟**：答完了的行写“答完到现在过了几分钟”，最多 44640（31 天）；别的行写 65535，表示不显示。卡片收到后用自己的时钟往上加，所以 Mac 不用因为时间流逝重发。
- **最长 226 字节**：4 + 6 × (1 + 1 + 2 + 1 + 32)。本机实测 Mac 每次最多写 512 字节（`status` 里的 `max_write`）。某台 Mac 少于 226 字节时，名字上限降到 24 字节（`name_limit`）。名字按 UTF-8 字符边界截断，不会切开一个汉字。
- **心跳**：只有 4 个字节 `01 <总数> 00 01`，不改画面。桥接程序每 30 秒发一次。卡片 90 秒没收到任何一帧（心跳或整表）就自己断开，让 Mac 重连；这 90 秒从版本核对一样的那一刻起算。

卡片对一帧查得很严：格式不是 1、标志位用了 bit0 以外的位、本帧行数不等于“总数和 6 取小的那个”、心跳不是正好 4 字节、行号是 0 或重复、状态不在 1 到 4、不是等你和出错却带“新进入”、分钟超出范围、名字超过 32 字节或不是合法 UTF-8 或含控制字符、末尾多出字节，都整帧拒绝，屏幕不变。

卡片从 USB 串口报这些行：收到整表报 `BLE rows total=<总数> shown=<行数> fresh=<0 或 1>`，收到心跳报 `BLE heartbeat`，拒绝时报 `BLE reject rows`（超过 226 字节时是 `BLE reject rows length`），90 秒没收到时报 `BLE silent rc=<返回码>` 并断开；连上、断开时报 `BLE connected`、`BLE disconnected reason=<原因码>`。断开时卡片清掉会话表，所以重连后不会先闪一下旧表。`info` 里的 `ble_writes` 是开机以来收到的有效 ROWS 帧数。串口命令 `rows` 打印卡片手上的会话表，每行 `ROW <行号> <状态名> <分钟或 -> <名字>`，最后一行 `OK rows total=<总数> shown=<行数> linked=<0 或 1>`；分钟是卡片自己累加后的数。

2026-10-25（实施计划 Task 3d）起卡片照着会话表画任务板，一行一个会话。收到的表第一行的状态变了时，卡片在串口上报 `STATE <状态名>`（等你 `waiting`、出错 `error`、在跑 `working`、答完了 `done`，空表 `idle`），测试靠它确认卡片收到了表。

卡片一次只接受一个连接，连上以后停止广播，断开后马上重新广播。

## 桥接程序怎么算状态

### 一个会话

每个会话（按 hook 输入里的 `session_id` 区分）记这几样：

- **行号**：1 到 255，第一次显示时分配，从上次用到的号往后找、跳过正在用的号，所以刚删掉的会话的号不会马上给别人。
- **项目名**：hook 送来的目录名，见下文“hook 模式的规矩”。
- **在做什么**：在跑、答完了、出错之一。
- **“等你”记录**：一组。有四种：`PermissionRequest` 记的（按“工具名 + 工具参数”认，带着那条还连着的 hook；选择题 `AskUserQuestion` 弹出时也走这一条）、`PreToolUse` 遇到 `ExitPlanMode`（计划确认）时记的（按 `tool_use_id` 认）、`Notification` 的 `permission_prompt` 记的（只有一条）、下一步框带问题时记的（只有一条，见下文“下一步框里的问题”）。
- **进入当前状态的时刻**、**`claude` 进程号**、**是否显示**（收到过 `UserPromptSubmit` 才显示）。

会话显示的状态：有“等你”记录时是等你，否则是“在做什么”。

| 事件 | 怎么改 |
| --- | --- |
| `SessionStart`（会话开始） | 记下项目名和进程号，不显示。压缩上下文（对话太长时 Claude Code 把前面的内容压成一段摘要）、`/clear`、恢复会话也会触发它 |
| `UserPromptSubmit`（用户发了指令） | 显示这个会话（第一次时分配行号），在跑，清掉全部“等你”记录 |
| `PreToolUse`（准备用工具） | 在跑；工具是 `ExitPlanMode` 时加一条“等你” |
| `PermissionRequest`（要用户批准） | 加一条“等你” |
| `Notification`，类型是 `permission_prompt` | 加一条“等你”。这是兜底：沙箱里的命令要上网时弹出的批准框不触发 `PermissionRequest`，只有这个通知，而且晚约 6 秒 |
| `PostToolUse` / `PostToolUseFailure`（工具用完 / 运行失败） | 在跑；去掉同一 `tool_use_id` 的计划记录、同一“工具名 + 工具参数”的第一条批准记录（放走它的 hook）和通知记录；hook 带 `asks: true` 时加一条问题记录 |
| 终端里拒绝，还连着的 `PermissionRequest` hook 被 Claude Code 结束 | 去掉这条记录和通知那条记录（两条记的是同一个弹窗，弹窗出现约 6 秒后才有通知）；没有别的记录时回到在跑 |
| `Stop`（答完一轮） | 答完了，清掉问题记录以外的“等你”记录；有问题记录时这一行仍显示等你 |
| `StopFailure`（因为接口出错结束这一轮，比如额度用完） | 出错了，清掉全部“等你”记录 |
| `SessionEnd`（会话结束） | 删掉这个会话。`/clear` 会先给旧会话发 `reason: clear` 的 `SessionEnd`，所以旧行消失、新会话发第一句话时出现新行 |

其中几条的理由：

- **为什么记“一组”等你记录**：Claude 可能一次发起几个要批准的操作。批准一个后，别的还在等，这一行应该仍然是等你。`PermissionRequest` 的输入里没有 `tool_use_id`，所以用“工具名 + 工具参数”认出是同一个操作；hook 对 `PostToolUse`、`PostToolUseFailure` 也算同样的指纹。
- **在终端拒绝（按 Esc 或选“3. No”）**：这时 Claude Code 不发出任何 hook 事件（实测见下文“实测结果”第 3 条），只结束还连着的 hook 进程，桥接程序看到连接断开就知道了（项目负责人 2026-10-16 选定，G23；FM-14 时的实测见 [approval.md](approval.md)）。
- **生成回答时按 Esc 打断**：这时没有 hook 事件，也没有在等的 hook 可以断开，光靠 hook 桥接程序无从得知。2026-10-16 负责人先确认就这样处理；2026-10-25 卡片上一个会话等一个卡片没收到的批准等了 5 个小时、一直显示“在跑”，所以改成定时核对，见下文“定时核对会话（SC-20）”。
- **为什么不用 `Notification` 的 `idle_prompt`**：它要等约 60 秒，实测只在正常答完一轮之后出现，打断以后不出现，纠正不了上一条。
- **为什么不读会话记录文件**：打断时会话记录文件（`transcript_path` 指向的 JSONL 文件）里会出现 `[Request interrupted by user for tool use]`，但这个格式不在官方文档里，升级后可能改变。

收到一个没见过的会话的事件（比如桥接程序中途重启过），就当它已经存在，按事件改。

### 定时核对会话（SC-20）

hook 事件会丢：生成回答时按 Esc 打断没有事件；桥接程序停着的时候（比如跑全套测试时）会话弹出的批准框，桥接程序永远收不到。所以桥接程序每 15 秒在后台跑一次 `claude agents --json`。这是 Claude Code 自带的命令，列出这台 Mac 上的每个会话，每项有 `sessionId` 和 `status`：`busy`（在忙）、`waiting`（在等人，`waitingFor` 写等什么，比如 `permission prompt`）或 `idle`（闲着）。2026-10-25 本机实测：每次 0.2 到 1.0 秒，用户态 CPU 约 0.15 秒；不会拉起后台管理进程；会话跑一条 25 秒的 Bash 命令时一直报 `busy`。

用哪个 `claude`：和 doctor 一样，在 PATH 上的和桌面 App 里版本最高的那份中挑版本较新的；第一次核对时挑，之后一直用它，找不到就下一次再挑。测试用 `serve --claude <路径> --agents-seconds <秒数>` 指定程序和间隔。

| 答案 | 怎么改 |
| --- | --- |
| `waiting`，这一行没有“等你”记录 | 加一条“核对看到的”等你记录（没有 hook），照常带“新进入”位、照常提醒 |
| 连续两次 `busy` | 去掉没有 hook 的等你记录，下一步框里的问题记录除外 |
| 连续两次 `idle` | 同上，再把“在跑”改成“答完了” |
| 只有一次 `idle`、列表里没有这个会话 | 不改 |

“连续两次”按这个会话算，中间收到这个会话的任何 hook 事件就重新数。核对开始以后这个会话送来过 hook 事件，这次的答案不算：hook 事件比核对新。命令运行失败、退出码不是 0、输出不是 JSON 数组或者数组里有不是对象的项时，什么都不改，也重新数。会话表是空的或者上一次核对还没回来时，不跑这条命令。工具用完（`PostToolUse`）时，“核对看到的”记录和通知记录一起去掉。

为什么要两次：一次 `idle` 可能只是两个工具调用之间的一瞬间；连续两次相隔 15 秒以上，会话在这段时间里又没有任何 hook 事件，才算真的停了。为什么 `busy` 也去掉旧的等你记录：批准框被处理后会话接着干活，但如果那次批准的 hook 事件丢了，等你记录会一直留着。

`status` 里的 `agents_check` 是最近一次核对的结果：`not_yet`（还没核对过）、`ok`、`no_claude`（找不到 `claude`）、`failed`（命令运行失败）或 `unreadable`（输出读不懂）。`--log` 记录里每次核对记一行 `kind: agents`，带 `result`，成功时 `seen` 写每个会话的答案。doctor 的“会话核对”一行读的就是它。

**测试**：[tests/test_agents_check.py](../tests/test_agents_check.py) 用一个假的 `claude`（记下每次参数，照测试写好的顺序一次给一个答案，也能故意失败或慢 1.5 秒再答）和真的卡片跑 8 种情况：看到等你后再看到在忙、闲着；只有一次在忙时等你留着，接着两次闲着直接变成答完了；在忙和单次闲着不改；每次核对前都有 hook 事件时不改；核对开始后才来的 hook 事件让这次答案不算；核对失败夹在两次闲着中间时重新数；还连着的批准 hook 和下一步框问题不受核对影响；失败、读不懂和列表里没有都不改，会话表空时不跑。把“核对开始后才来的事件不算”和“失败后重新数”两处代码故意去掉后，对应的 2 项失败，卡片变成了答完了。第 9 项用真的 `claude` 开会话跑一条 40 秒的命令（`sleep 40` 写在脚本里，因为 Claude Code 会拦下单独一条 `sleep 40`），每 2 秒核对一次：2026-10-25 实测命令跑了 41.8 秒，期间核对 21 次全是 `busy`，卡片只有“干活中 → 完成了”（`artifacts/sc20-*/agents/`）。命令刚开始时那次核对如果早于 `PreToolUse`，按规则不算，记录里这个会话没有答案。

**进程已经不在的会话**：Claude Code 被直接结束（`SIGKILL`）时没有 `SessionEnd`。桥接程序每 5 秒对每个会话的进程号做一次 `kill(pid, 0)`，进程不在就删掉这个会话，记一行 `session_gone`。桌面 App 里关掉会话时进程不退出，这一行留到归档会话为止，归档时有 `SessionEnd`（负责人 2026-10-24 决定）。

**会话表存盘**：会话表每次有变化都写到 `<套接字路径>.sessions.json`。桥接程序启动时读回来（记一行 `loaded`），马上核对一遍进程号。Mac 重启或桥接程序崩溃后，还在跑的会话因此不会从卡片上消失。

### 几个会话同时在跑

桥接程序把显示着的会话排好：等你 → 出错 → 在跑 → 答完了；同一种状态按项目名的 Unicode 码位排；再按行号。取前 6 行，连同总数写给卡片。被挤掉的总是排在后面的，所以等你的行不会因为会话太多而看不到。两个会话的项目名一样时显示两行同样的名字。

**新进入**：一个本来就显示着的会话从别的状态变成等你或出错时，下一帧里这一行带“新进入”位，之后的帧不再带。两个同名会话先后变成等你，各带一次。重连后重发整表、别的行变了而重发时都不带。

### 卡片断开再连上

桥接程序只在会话表变了（总数，或者显示的某一行的行号、状态、进入时刻、项目名变了）时写一帧；写入要等卡片确认，确认之前表又变了，就在确认后写最新的那张，中间的不补写。写失败 1 秒后重试。每次连上卡片（包括卡片重启、刷了新固件后），版本核对一样后先写一次整表。

Mac 合盖睡眠时蓝牙连接不一定断，醒来后桥接程序只收到“蓝牙可用了”。所以蓝牙变成可用时，桥接程序先问 macOS 有没有已经连着、带这个服务的卡片（`retrieveConnectedPeripherals`，记一行 `retrieved`），有就直接用，没有才扫描。卡片刷了新固件、功能表变了时，macOS 会通知桥接程序（`didModifyServices`），桥接程序重新读一遍功能表。桥接程序正常退出（`quit`）前先断开蓝牙，最多等 1 秒，卡片马上知道没人连着。

### 先核对版本（OB-13）

卡片固件和桥接程序各有一个连接协议版本号（两边约定怎么收发数据的版本，是一个十进制整数），2026-10-24 起都是 3（换成 ROWS 时从 2 升上来）。卡片服务里有一个特征值 VERSION，编号 `6d2f1008-…`，和 ROWS 一样要配对加密后才能读写，内容是不带空格、不以 0 开头的十进制数字，1 到 9999。

每次连上卡片，桥接程序先读 VERSION，再把自己的版本号写回去，等卡片确认后再看两边是否一样：

- **一样**：记一行 `version`（`card`、`bridge`、`match` 是 `true`），然后写一次整张会话表。
- **不一样**：记一行 `version`（`match` 是 `false`），断开，不再重连。`status` 里 `card` 是 `mismatch`。卡片那边收到写回的版本号后，整屏换成红底白字的“版本不配 / 卡片 2 · Mac 3”（数字是两边实际的版本），下面写该更新哪一边：Mac 的版本大时是“请更新卡片固件”，卡片的版本大时是“请更新 Mac 上的桥接程序”，最后一行是“然后重启桥接程序”。这个画面一直保留，直到版本一样的桥接程序连上来。
- **找不到 VERSION**（OB-13 之前的固件）：同样算不一样，`version` 那一行的 `card` 是 `null`。旧固件没有这个画面，卡片停在原来的显示上。2026-10-18 把 OB-13 之前的固件只写进程序分区（配对信息不动）测过一次：桥接程序连上 1 次，记一行 `version`（`card` 是 `null`），断开时 `reconnect` 是 `false`，15 秒后 `status` 仍是 `mismatch`、`connects` 仍是 1；`doctor` 报“卡片固件太旧，没有版本号”。测完写回了新固件（`artifacts/ob13-oldfirmware-20261018-101801/`）。这一项是手动做的，没有写成自动测试，因为每次都要换两次固件。
- **读到的不是 1 到 9999 的数字**：记一行 `version_unreadable`（字节数和错误），断开后照常重连。
- **读不出，错误是“加密不够”或“认证不够”**（`CBATTErrorDomain` 的错误码 15 或 5）：说明这条连接没配对成功，比如配对框被取消。`version_unreadable` 那一行多一个 `pairing_failures`，是连续失败的次数；断开后照常重连，macOS 在新连接上会再弹配对框。连续失败 3 次后，`status` 里 `card` 变成 `pairing_failed`，桥接程序停止扫描、不再重连，免得配对框一直弹下去；重启桥接程序或蓝牙重新打开后从 0 算起，连上一次（记 `ready`）也清零。OB-14 加的，实测见 [approval.md](approval.md) 的“实测结果”第 11 条。

不重连是有意的：版本对不上时，重连多少次结果都一样，只会让卡片反复断开。想重试，就更新落后的那一边后退出再启动桥接程序；关掉再打开 Mac 的蓝牙也会让它重新搜一次。

`status` 多了两项：`card_version`（这次连接读到的卡片版本，还没读到或者卡片没有 VERSION 时是 `null`）和 `bridge_version`（桥接程序自己的版本）。`serve` 可以加 `--link-version <1-9999>`，让桥接程序假装是别的版本，只给测试用：这样不用另外编译一个桥接程序，也就不用再点一次蓝牙授权。

旧的桥接程序（不认识 VERSION）连新固件时，不读也不写 VERSION，卡片照常收状态，屏幕不出现版本画面。2026-10-18 用 OB-13 之前编译的桥接程序配新固件跑了 `test_bridge.py`、`test_card_display.py` 和 `test_approval.py`：42 项通过、3 项照常跳过，6 项因为常驻程序中途连走了卡片而失败（见下文“卡片测试期间挡住常驻程序”），加锁后重跑这 6 项全部通过。

[tests/test_link_version.py](../tests/test_link_version.py) 在真实卡片上测三种情况，2026-10-18 10:16 全部通过（`artifacts/ob13-20261018-101634/`）：版本一样时照常连上、写状态；桥接程序假装是 3 或 1 时，各只连 1 次，15 秒里不再重连，没有写状态，卡片显示对应的提示，截图里三行字都在；之后启动版本一样的桥接程序，卡片恢复正常。

## 下一步框里的问题

下一步框是 Claude Code 电脑端在一轮结束时显示的小结框，由工具 `mcp__ccd_turn__wrap_up`（桌面 App 内部的工具名，App 改名时这里要跟着改）画出来，参数 `ask` 是框里的问题。2026-10-25 实测（`artifacts/g22-probe-20261025-183829/`）：带问题的下一步框只发这个工具的 `PreToolUse`、`PostToolUse`，然后是 `Stop`，没有 `PermissionRequest`，所以原来显示“答完了”。选择题 `AskUserQuestion` 弹出时会发 `PermissionRequest`，本来就显示“等你”。

- hook 看到这个工具的 `ask` 是不为空的文字时，只多传一个 `asks: true`，不传问题和小结本身。
- 桥接程序在这个工具的 `PostToolUse` 时加一条问题记录（`PostToolUseFailure` 不加：工具失败说明框没画出来），所以“等你”比 `Stop` 早几秒出现。`Stop` 不清这条记录。
- 你发下一句指令（`UserPromptSubmit`）、这一轮出错（`StopFailure`）或会话结束（`SessionEnd`）时清掉。之后的 `PreToolUse`、`PostToolUse` 不清，因为子代理（Claude 派出去做一部分工作的助手）和主会话用同一个 `session_id`，它的工具事件可能在下一步框之后才到。
- 做不到的：子代理做完后自动开始的一轮也有 `UserPromptSubmit`，会清掉问题记录；那一轮再次用下一步框提问时才回到“等你”。

## hook 模式的规矩

- **从不挡住 Claude Code**：桥接程序没在运行、套接字连不上、输入不是 JSON，都直接退出，退出码是 0。唯一的例外是 `SessionStart`：连不上时先启动桥接程序，最多等 3 秒，见下文“会话开始时启动桥接程序”。连接和读写都有 1 秒上限；`PermissionRequest` 不同，桥接程序确认收到请求最多等 2 秒，之后一直连着，见下文“等你批准时 hook 怎么等”。hook 命令本身的参数写错时（比如 `--socket` 后面没有路径），退出码是 64；按官方文档，退出码不是 0 也不是 2 的 hook 算“不挡事的出错”，操作照常进行，会话记录里会多一条 `hook error` 提示。
- **不往标准输出写任何东西**：`SessionStart` 和 `UserPromptSubmit` 的 hook 往标准输出写的内容，会被 Claude Code 当成上下文交给 Claude。
- **要批准时一直连着**：`PermissionRequest` 的 hook 不马上退出，规则见下文“等你批准时 hook 怎么等”。它从不回答，所以批准只能在电脑上做。其他事件仍然马上退出。
- **只传需要的几项**：事件名、`session_id`、工具名、`SessionStart` 的 `source`（会话怎么开始的，比如 `startup`、`compact`）、`SessionEnd` 的 `reason`（会话为什么结束）、`StopFailure` 的 `error`（出错类型），“工具名 + 工具参数”的 SHA-256 校验值（一种内容指纹，内容差一个字也不同，`PermissionRequest`、`PostToolUse`、`PostToolUseFailure` 都算），`tool_use_id`（Claude Code 给每次用工具的编号），`Notification` 的 `notification_type`（通知类型，桥接程序只认 `permission_prompt`），`claude_pid`（这个 hook 属于哪个 `claude` 进程，用来清理进程已经不在的会话；有环境变量 `CLAUDE_PID` 时用它，否则用 hook 的父进程号），`project`（项目名），以及 `asks`（只在下一步框带问题时出现，值是 `true`）。不传工具参数本身、命令内容、文件内容、完整的工作目录或用户的指令。
- **项目名只传目录名**：取环境变量 `CLAUDE_PROJECT_DIR`（会话启动时的项目根目录，Claude 在会话里 `cd` 也不变）的最后一级；没有这个变量时，只在 `SessionStart` 时取 `cwd` 的最后一级。这个目录里的 `.git` 是文件而不是目录时（git worktree，也就是同一个仓库另开的一份工作副本），读它的 `gitdir:` 一行，指向 `<主仓库>/.git/worktrees/<名字>` 时取主仓库的目录名，所以工作副本里的会话和主仓库的会话显示同一个项目名。以前 `PermissionRequest` 多传一段要显示在卡片上的 `summary`，2026-10-24 起不传了。

## 等你批准时 hook 怎么等

`PermissionRequest` 的 hook 发 `{"op":"wait", …}`，桥接程序回 `{"ok":true,"id":<编号>}`，之后两边都不再说话，连接一直开着。卡片显示“等你批准”，直到下面几种情况之一：

- **在终端答了，工具接着跑**：桥接程序收到同一个会话、同一个“工具名 + 工具参数”的 `PostToolUse` 或 `PostToolUseFailure`，就关掉自己这一头的写方向（`shutdown` 的 `SHUT_WR`），hook 读到连接结束后退出。记录里依次是 `wait_released`（`why` 是 `post_tool_use`）和 `wait_closed`（`how` 是 `released`）。
- **这个会话往下走了**：同一个会话的 `UserPromptSubmit`、`Stop`、`StopFailure`、`SessionEnd` 放走这个会话所有在等的 hook，`why` 分别是 `prompt`、`stop`、`stop_failure`、`session_end`。
- **在终端拒绝**：Claude Code 结束 hook 进程，桥接程序看到连接断开，记 `wait_closed`（`how` 是 `hung_up`），去掉这条“等你”记录，会话没有别的记录时回到在跑。
- **hook 等到自己的上限**：上限默认 590 秒，比 `hooks.json` 给它的 600 秒少一点。到点时 hook 发 `{"op":"give_up"}` 后退出，桥接程序记 `wait_gave_up` 和 `wait_closed`（`how` 是 `gave_up`）。这条“等你”记录留着，但不再带 hook，卡片上这一行仍是等你，因为终端里的批准弹窗还在。`hook` 可以加 `--wait-limit <秒>` 换上限，只给测试用。

为什么不让 hook 马上退出：终端里拒绝时没有任何 hook 事件，只有这条还连着的 hook 被结束，桥接程序才知道该把卡片改回来。

## 会话开始时启动桥接程序

OB-9 起，`hook` 模式收到 `SessionStart` 时，如果套接字连不上（套接字文件不存在，或者是上次崩溃的桥接程序留下的），就自己启动桥接程序，等它就绪后再把事件交给它。负责人 2026-10-17 选定由 hook 模式启动，不由 mod 启动（`.agents/tasks/onboarding/goal.md` 的 G20），因为公司用 `allowManagedModsOnly` 只关掉 mod 时，hooks 照样能启动桥接程序和显示状态。

- **怎么启动**：运行 `open -n -g <hook 程序所在的 .app> --args serve --socket <套接字路径>`。用 `open` 是因为桥接程序用蓝牙，必须由 macOS 自己启动（见上文“整体结构”）；这样它也不是会话的子进程，会话结束后照常运行。`-n` 表示即使这个 App 已经有一份在跑（比如在别的套接字上），也再开一份。套接字路径总是写在参数里，因为 `open` 不把环境变量 `FUNMEDAL_SOCKET` 交给新程序。hook 自己带了 `--log` 时，也原样交给新程序，测试靠它看新程序的记录。`open` 的标准输出和错误输出都丢掉：`SessionStart` 的 hook 往标准输出写的内容会进 Claude 的上下文。
- **等多久**：启动后每 0.05 秒试连一次套接字，最多 3 秒。连上就只发一次事件；3 秒内没连上就不发，照常退出，退出码 0。`SessionStart` 的 hook 上限是 5 秒（`plugin/hooks/hooks.json`）。实测冷启动 1.34 秒，套接字留着旧文件时 0.14 秒（`artifacts/ob9-nocard-20261018-010607/`）。
- **两个会话同时开始**：两个 hook 可能都连不上、各启动一份。后启动的那份拿不到套接字旁边 `.lock` 文件的锁，以退出码 3 自己结束（见“怎么配置”第 3 步），两个 hook 都连到先启动的那份。实测两个同时开始各用 0.15 秒，最后只剩一份，两个事件都到了。
- **其它事件不启动**：`SessionStart` 以外的 8 种事件连不上时照旧 1 秒内退出，什么也不启动，测试里等了 3 秒也没有桥接程序出现。

## 怎么配置

1. **编译**：运行下面的命令，生成 `mac/bridge/build/FunMedalBridge.app`。需要 Xcode 命令行工具里的 `swiftc`（Swift 编译器）。脚本用钥匙串里第一张 Apple Development 证书签名，一张都没有时用临时签名（`codesign --sign -`，只在本机有效、不用证书的签名），见下文“签名（OB-10）”。

   ```bash
   sh mac/bridge/build.sh
   ```

2. **启动常驻程序**：装上插件后，会话开始时会自动启动（见上文“会话开始时启动桥接程序”），这一步只在想先启动、或者不用插件时才需要。`-g` 表示在后台打开，不抢走当前窗口。不加 `--socket` 时，套接字在 `~/Library/Application Support/FunMedal/bridge.sock`。想留记录就加 `--log <文件路径>`，收到的事件、蓝牙连接和每次写入都会记成一行 JSON。第一次启动时 macOS 会问是否允许它使用蓝牙，选允许。**每次改了代码重新编译后，macOS 都会再问一次**：临时签名没有固定的身份，macOS 按程序内容的指纹记住授权，内容变了就当成新程序。2026-10-16 到 17 日系统授权日志（`tccd` 进程的日志）里有 6 次这样的询问，每次都是用户点的允许；询问没人回答时，桥接程序一直连不上卡片，`status` 里 `authorization` 是 `notDetermined`。

   ```bash
   open -g mac/bridge/build/FunMedalBridge.app --args serve
   ```

3. **查看和停止**：`funmedal-bridge` 是 `.app` 里的程序，路径是 `mac/bridge/build/FunMedalBridge.app/Contents/MacOS/funmedal-bridge`。`status` 打印一行 JSON，其中 `card` 是 `connected` 表示连上了卡片，`synced` 是 `true` 表示卡片已经确认收到当前的会话表。`quit` 让常驻程序退出。同一个套接字上已经有常驻程序时，再启动一个会马上以退出码 3 结束，第一个不受影响；用 `open` 启动时看不到这个退出码，用 `status` 看 `pid` 有没有变就知道。

   ```bash
   mac/bridge/build/FunMedalBridge.app/Contents/MacOS/funmedal-bridge status
   ```

4. **接上 Claude Code**：运行仓库根目录的 `install.sh`，它把桥接程序复制到 `~/Applications/FunMedalBridge.app`，再从本仓库这个插件市场装上 `funmedal` 插件。插件的 [plugin/hooks/hooks.json](../plugin/hooks/hooks.json) 给 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`Notification`、`PostToolUse`、`PostToolUseFailure`、`Stop`、`StopFailure`、`SessionEnd` 这 10 个事件各配一条同样的命令 `"$HOME/Applications/FunMedalBridge.app/Contents/MacOS/funmedal-bridge" hook`；`PermissionRequest` 那一条的 `timeout` 是 600，其他是 5；`Notification` 那一条只接 `permission_prompt` 类型（`matcher`）。命令运行固定位置的程序，不运行仓库里的文件：挪走仓库后，已经开着的会话的 hook 不会因为找不到文件而以退出码 2 结束（退出码 2 会拦下工具调用）。桥接程序没装时，shell 找不到程序，以退出码 127 结束，Claude Code 照常往下走。

   不带 `--socket` 时，各个模式先看环境变量 `FUNMEDAL_SOCKET`，有值就用它作套接字路径，没有才用默认路径。测试用 `claude --plugin-dir plugin` 加载插件，并给会话设 `FUNMEDAL_SOCKET`，让插件的 hooks 连到本次测试自己的常驻程序。

   **卡片测试期间挡住常驻程序**：卡片一次只接受一个蓝牙连接。2026-10-18 凌晨，测试跑到一半时，默认套接字上的常驻程序两次被插件的 `SessionStart` hook 启动起来，连走了卡片，测试用的桥接程序 60 秒里搜不到卡片，6 项失败（`artifacts/ob13-oldbridge-20261018-014413/`）。01:46 那次是本项目的 Claude 会话压缩上下文；01:51 那次来源没查实，测试自己开的会话不会这样，因为它们的 hook 只连测试的套接字。这是第三次因为常驻程序占着卡片而测试失败：前两次是测试开始前它就在跑，夹具（测试开始前准备卡片的那段代码）只在开始时查一次，挡不住中途被启动的。当时的办法是让 [tests/bridge_harness.py](../tests/bridge_harness.py) 的 `card` 夹具在整个测试文件运行期间用 `flock`（一种文件锁，同一时间只有一个进程能拿到）占着默认套接字的 `bridge.sock.lock`，`serve` 拿不到这把锁就以退出码 3 结束。2026-10-24 常驻程序又在两个测试文件之间的空当里被启动起来，所以改成整轮 pytest 从头到尾拿着这把锁，原因和重现见 [docs/lessons.md](../docs/lessons.md)。[tests/test_card_guard.py](../tests/test_card_guard.py) 照插件的真实路径送一个 `SessionStart` 事件，再看 10 秒：加锁前常驻程序起来了、卡片被连走（`artifacts/guard-before-20261018-015420/`），加锁后常驻程序起不来、卡片一直在广播（`artifacts/guard-after-20261018-015445/`）。之前失败的 6 项加锁后重跑全部通过（`artifacts/ob13-oldbridge-rerun-20261018-015518/`）。

上面第 2、3 步和默认套接字路径实际跑过一次，记录在 `artifacts/fm13-default-socket-20261016-222621/`。第 4 步的 `install.sh` 由 `tests/test_plugin.py` 用真的 `claude` 在临时 `HOME` 里装过两遍；README 里“卸载”一节的 `uninstall.sh` 由 `tests/test_uninstall.py` 在临时 `HOME` 里接着装好的插件卸过两遍，之后插件列表、插件市场列表和三个设置文件里都找不到 FunMedal；真实会话测试走 `--plugin-dir`，不经插件市场。

| 10 | 上次桥接程序崩溃留下了套接字文件 | 新的桥接程序照常启动 | 留一个空的套接字文件再启动 |
| 11 | 同一个套接字上已经有一个桥接程序在跑 | 第二个拒绝启动，第一个不受影响 | 启动两个 |
| 12 | hook 把工具参数、命令、指令内容或工作目录传了出去 | 套接字上收到的每条消息只有“只传需要的几项”列出的字段，没有测试塞进去的那串内容 | 测试自己在套接字另一头收下 hook 发出的消息，6 种事件各一次 |

| 14 | Mac 蓝牙关掉再打开 | 关掉后桥接程序报蓝牙已关、卡片报断开；关着时会话变成“完成了”；打开后桥接程序自己重连，卡片显示“完成了”，并且只显示这一次 | 要你本人在控制中心关开蓝牙，设环境变量 `FM_BLUETOOTH_TOGGLE_SECONDS`（每一步最多等多少秒）才运行，平时跳过；模拟 hook 事件 + 真实蓝牙 |
| 15 | 会话开始时没有桥接程序（没有套接字文件，或者留着旧的） | hook 启动 hook 程序所在的 App，5 秒内退出，退出码 0，标准输出为空；新程序的父进程是 `launchd`（进程号 1），收到这个 `SessionStart` | 直接运行 hook（`tests/test_bridge_start.py`，OB-9） |
| 16 | 两个会话同时开始，都没有桥接程序 | 最后只剩一个桥接程序，两个事件都到；之后再开始一个会话不再启动 | 同时运行两个 hook，再运行一个 |
| 17 | 等批准的 hook 等到上限、被放走、或进程被结束 | 等到上限时记 `gave_up`，卡片仍是等你批准；被五种事件放走时记 `released` 和对应的 `why`；进程被结束时记 `hung_up`，会话回到在跑 | 模拟 hook 事件（`test_hook_gives_up`、`test_events_release_waiting_hooks`、`test_ended_hook_counts_as_answered`） |
| 18 | 真实会话开始时没有桥接程序 | `~/Applications` 里的桥接程序被启动，会话结束后还在；卡片依次显示干活中、完成了、空闲 | 真实 Claude Code 会话 |

“模拟 hook 事件”是把和 Claude Code 格式相同的 JSON 交给真实的 `hook` 命令，经过真实的套接字、蓝牙和卡片，只是不启动 Claude Code。这样能稳定地重现几个会话、几个操作同时等批准这类真实会话里难以控制的情况。

## status 和记录里的等待信息

`status` 打印的 JSON 里和等批准有关的两项：

- `waits`：还连着的 `PermissionRequest` hook，每个有 `id`（编号）和 `session`，最早的排在最前。
- `sessions` 里每个会话的 `state`（显示的状态：`waiting`、`error`、`running`、`done`）、`project`、`row`（行号）、`visible`、`pid` 和 `waiting`（还有几条“等你”记录）。hook 等到上限退出后，`waits` 里没有它了，`waiting` 仍算它。

和会话表有关的几项：`total`（显示着的会话数）、`rows`（排好后的前 6 行，每行 `row`、`state`、`minutes`、`project`）、`synced`、`frame`（现在该写给卡片的一帧，十六进制，不带“新进入”位）、`card_frame`（卡片最近确认收到的一帧）、`max_write` 和 `name_limit`（见上文“卡片怎么收状态”）、`heartbeats`（发了几次心跳）。`--log` 记录里每次写入记 `write`、确认记 `ack`，都带 `what`（`rows` 或 `heartbeat`）和 `frame`。

`--log` 记录里多了几种行，`kind` 是：

| `kind` | 什么时候记 | 字段 |
| --- | --- | --- |
| `wait` | hook 送来一个批准请求 | `id`、`session` |
| `wait_released` | 桥接程序放走了一个 hook | `id`；`why` 是 `post_tool_use`、`prompt`、`stop`、`stop_failure` 或 `session_end` |
| `wait_gave_up` | hook 等到自己的上限 | `id` |
| `wait_closed` | 和 hook 的连接结束 | `id`；`how` 是 `released`（被放走）、`gave_up`（等到上限）或 `hung_up`（hook 被结束，也就是终端里拒绝了） |

## doctor 自检

`funmedal-bridge doctor` 依次查 10 项，每项打印一行：`<结论> <项目>：<情况>`，结论不是“好”时后面接 `。改法：<怎么做>`。结论有四种：“好”；“注意”（能用，但有你该知道的事）；“不好”；“不知道”（查不了，后面写原因）。有一项“不好”时退出码是 1，否则是 0。

| 项目 | 从哪里查 | 怎么判断 |
| --- | --- | --- |
| 桥接程序 | 向套接字（默认路径，或 `--socket` 指定的）发 `status` | 有回应是“好”，没有是“不好” |
| 蓝牙 | `status` 里的 `authorization` 和 `bluetooth` | `allowedAlways` 且 `poweredOn` 是“好”；拒绝、还没回答授权框、蓝牙关着都是“不好” |
| 签名 | 对 `~/Applications/FunMedalBridge.app` 运行 `codesign --verify` 和 `codesign -dv` | 用证书签名是“好”；临时签名是“注意”，因为每次重新安装 macOS 都要再问一次授权，改法是拿一张 Apple Development 证书后重新编译、安装；没装、没签名或签名坏了是“不好” |
| 卡片 | `status` 里的 `card` | `connected` 是“好”；`mismatch`、`pairing_failed` 和其他没连上的情况是“不好”，`pairing_failed` 的改法是重启桥接程序后重新配对；`off` 是“不知道”，看蓝牙那一行 |
| 固件版本 | `status` 里的 `card_version` 和 `bridge_version`，见上文“先核对版本” | 一样是“好”；不一样、卡片没有版本号、正在跑的桥接程序太旧不报版本都是“不好”，并说该更新哪一边；卡片没连上是“不知道” |
| 插件 | 用下面两行里版本较新、能读出版本的那份 Claude Code 运行 `plugin list --json` | `funmedal@funmedal` 装着且开着是“好”；没装、关着是“不好”，关着时改法同时写桌面 App 的“+ → Plugins → Manage plugins”和终端的 `claude plugin enable`；两份都找不到是“不知道” |
| hooks 开关 | `~/.claude/settings.json` 里的 `disableAllHooks` | 是 `true` 时“不好”，其他情况（包括没有这个文件）是“好” |
| 会话核对 | `status` 里的 `agents_check`，见上文“定时核对会话（SC-20）” | `ok` 和 `not_yet` 是“好”；`no_claude`、`failed`、`unreadable` 是“注意”，各写改法；正在跑的桥接程序太旧不报这一项是“注意”，改法是重新运行 `install.sh`；桥接程序没在跑是“不知道” |
| Claude Code 版本（终端） | PATH 上的 `claude --version` | 不低于 2.1.292 是“好”，和 `install.sh` 的要求一样；读不出版本号是“不知道”；低于 2.1.292 时，另一行够新就是“注意”（用另一份开会话不受影响），否则是“不好”；没找到时，另一行找到了就是“好”，两行都没找到是“不好” |
| Claude Code 版本（桌面 App） | `~/Library/Application Support/Claude/claude-code/<版本>/<编号>/claude.app/Contents/MacOS/claude` 里能读出版本的、版本最高的那份运行 `--version` | 判断同上一行。桌面 App 升级后旧版本目录还留着，所以只看最高的那份；2026-10-18 本机 10 月 17 日以后启动的桌面会话都用目录里最高的 2.1.299 |

蓝牙授权必须问正在跑的桥接程序：macOS 按程序记授权，在终端里运行的 `doctor` 自己去读，读到的是终端的授权，不是桥接程序的。所以桥接程序没在跑时，这一项和卡片、固件版本一起显示“不知道”。2026-10-24 以前还有一项“语音识别”，随按住说话一起删了。

**没查的**：`disableAllHooks` 只看用户设置文件，不看项目里的设置和公司统一下发的设置；`--safe-mode` 启动的会话也查不出来。

**测试**：[tests/test_doctor.py](../tests/test_doctor.py) 用一个假的桥接程序套接字（按测试给的内容回答 `status`）、一个假的 `claude` 命令和临时家目录，先造“全都正常”的环境，再每次只弄坏一处，当时一共 20 种情况（2026-10-24 去掉了语音识别的 2 种），检查每一行的结论、改法和退出码（`artifacts/ob11-20261018-015646/`）。把比较卡片和桥接程序版本的判断故意写反后，相关的 2 项失败（`artifacts/ob11-bug-back-20261018-015732/`）。签名的“好”造不出来：要先定下用哪种证书签名。OB-10 之后，仓库编译的桥接程序用证书签名，假程序直接复制它，“全都正常”里签名一项就从“注意”改成了“好”；临时签名另算一种情况（`app-adhoc`），是“注意”并给出改法。2026-10-18 在本机真实环境里跑过两次（`artifacts/ob11-real-20261018-015809/`）：常驻程序没在跑时，桥接程序一项“不好”、4 项“不知道”；启动常驻程序后，只剩固件版本“不好”，因为装着的常驻程序是 OB-13 之前编译的，不报版本号，`doctor` 提示重新运行 `install.sh`。

OB-17 起版本拆成终端和桌面 App 两行，测试另加 9 种情况（`test_doctor_desktop`）：假家目录里按桌面 App 的目录结构放假的 `claude`，查只有桌面 App、桌面目录里最高那份坏了、两边都够新、一边太旧另一边够新、只有一份旧的桌面版、终端读不出版本号、两边都没有、桌面用户的插件关着。故意把“另一边够新时报注意”改成“不好”后，两个相关用例失败（`artifacts/focus-ob17-bug-back-20261018-172832/`）。

## 签名（OB-10）

macOS 记蓝牙授权时（2026-10-24 以前还有语音识别授权），记的是程序编号加签名里的“认定规则”（designated requirement，macOS 用来判断“是不是同一个程序”的条件，`codesign -d -r- <App 路径>` 能打印出来）。下次启动时，程序满足这条规则才算同一个程序，授权才照旧有效（苹果技术说明 TN3127）。

- **临时签名**：认定规则是程序内容的哈希 `cdhash`。改一个字重新编译，哈希就变，macOS 当它是新程序，再问一次授权。2026-10-18 改之前跑 `tests/test_signing.py`：仓库编译的那份是 `cdhash H"48e3…"`，只在 `Info.plist` 里多加一个键再编译的那份是 `cdhash H"5fbe…"`（`artifacts/ob10-before-20261018-143023/`）。
- **Apple Development 证书**：认定规则是“程序编号是 `com.funmedal.bridge`、证书由苹果签发、证书上的名字是 `Apple Development: <名字>`、中间证书是苹果的开发者证书”，和程序内容无关。本机钥匙串里有两张同名的证书（2027-04 和 2027-05 到期），分别签出的认定规则一字不差。
- **实测（2026-10-18）**：换成证书签名后，第一次启动常驻程序又弹了语音识别和蓝牙授权框，负责人点了允许。之后 `tests/test_signing.py` 编译一份内容不同的桥接程序（内容哈希 `42489…`，仓库那份是 `493c…`），认定规则相同，启动后直接是 `allowedAlways` 和 `authorized`，连上卡片，没有弹框（`artifacts/ob10-after-20261018-143509/`）。再用另一张同名证书签一份内容不同的，3 秒内同样直接拿到授权并连上卡片（`artifacts/ob10-second-cert-20261018-143620/record.txt`，手动做的，没写成测试）。
- **没走过的**：README 第 3 步在 Xcode 里拿证书的几步，本机没有走过，因为钥匙串里已经有证书，本机也没装 Xcode；证书到期后换新证书会不会再问授权，也没测过，同名的新证书认定规则不变，按道理不会再问。
- `build.sh` 用 `security find-identity -v -p codesigning` 列出的第一张 Apple Development 证书。名字不同的证书签出的规则不同，换用另一个 Apple ID 的证书后，第一次启动会再问一次授权。

## 实测结果

以下都在本机终端版 Claude Code 2.1.292、真实卡片和真实蓝牙上测得。

1. **真实会话的状态顺序**：发指令、要批准、在终端批准、答完、退出，卡片依次显示干活中、等你批准、干活中、完成了、空闲，和桥接程序写出的顺序一致。记录在 `artifacts/fm13-real-20261016-221449/`。
2. **等你批准的延迟**：从桥接程序收到 hook 送来的 `PermissionRequest` 到卡片报 `STATE waiting` 用了 0.05 秒。记录同上。Claude Code 弹出批准窗口到 hook 进程把事件送到桥接程序的时间不在里面；FM-8 实测弹窗和 hook 开始的时间相差不到 0.1 秒。
3. **在终端拒绝**：批准弹窗有两种拒绝方式，按 Esc 和选“3. No”，结果一样：屏幕显示 `Interrupted · What should Claude do instead?`，之后不再有 hook 事件。按 Esc 那次 93 秒里都没有，直到测试结束会话时才收到 `SessionEnd`（`artifacts/fm13-real-20261016-221642/`）；选“3. No”那次 20 秒里没有（`artifacts/fm13-reject-no-probe-20261016-224738/`，里面有探测脚本）。按这个结果定下第 3 种情况的期望后，两种方式的测试都通过（`artifacts/fm13-focused-20261016-225144/`）：拒绝后 15 秒内卡片一直是等你批准，发下一条指令后依次是干活中、完成了。生成回答时按 Esc 打断，官方文档写明 `Stop` 不会触发，FM-13 没有单独实测。
4. **`idle_prompt` 什么时候出现**：一轮正常答完（`Stop`）后 60.06 秒出现。记录和探测脚本在 `artifacts/fm13-idle-probe-20261016-221933/`。
5. **卡片重启**：卡片执行 `reboot` 后 0.44 秒打出 `READY`，0.96 秒时已重新连上并恢复成重启前的状态。记录在 `artifacts/fm13-focused-20261016-221112/`。卡片用 `esp_restart`（ESP-IDF 里让芯片从软件重启的函数）重启时 USB 串口不断开，Mac 上的串口一直能读。
6. **卡片任务的栈余量**：`stacks` 报的是开机以来每个任务栈空间最少时还剩多少。`artifacts/fm13-focused-20261016-225144/` 那次，卡片烧完固件后开机 92 秒，期间跑过两次真实会话的拒绝测试和大输入测试，收到 14 次状态写入，读到：按键 2600 字节、屏幕 3440 字节、串口命令 1740 字节、蓝牙 1452 字节（蓝牙任务一共 4096 字节）。测试要求每个任务至少剩 1024 字节，完整测试里这一项在其余蓝牙测试都跑完后检查，每次的数字记在结果目录的 `bridge/card-stacks.txt`。
7. **hook 传出去的内容**：测试在套接字另一头收下 7 种事件的消息，每条只有 `op`、`event`、`session` 和该事件对应的 `tool_name`、`tool_key`、`source`、`reason`、`error`，没有测试塞进工具参数、指令、回答内容里的那串字符（`artifacts/fm13-focused-20261016-225144/bridge/hook-captured.json`）。
8. **Mac 蓝牙关掉再打开**（编号 14），2026-10-17 15:34：你在控制中心把蓝牙关了 23.1 秒。关掉后卡片报 `BLE disconnected reason=0x213`（对方主动断开），桥接程序把卡片标成 `off`；打开后 4.1 秒重新连上，4.7 秒时卡片确认显示“完成了”（`artifacts/fm13-bluetooth-toggle-20261017-153325/`）。前一次运行里程序的表现一样，但测试在关蓝牙之前读桥接程序状态读早了：卡片刚报收到“干活中”，桥接程序还没收到卡片的确认，所以测试失败（`artifacts/fm13-bluetooth-toggle-20261017-152842/`）；之后测试改成等桥接程序收到确认。再前一次没有人关蓝牙，测试等了 2 分钟超时（`artifacts/fm13-bluetooth-toggle-20261017-135530/`）。关蓝牙时桥接程序先收到“卡片断开了”，约 0.06 秒后才收到“蓝牙已关”；这段时间里它照常马上重连，每次都失败（`Local device is powered off`，macOS 的意思是“本机蓝牙已关”），一共 56 次，收到“蓝牙已关”就停了，不影响结果。桥接程序重连失败后不等待就再连，这一点没有改。
9. **换固件后 Mac 用旧的功能表**：卡片换上带语音的固件后，Mac 一直用旧固件的功能表，桥接程序找不到语音的 3 项，连不上。原因和改法见 [firmware.md](firmware.md) 的“换固件后 Mac 还用旧的功能表”。

## 还没做的

- **打断后卡片要晚一点才改**：定时核对要连续两次看到闲着，所以打断后这一行最多约 30 秒后才从“在跑”变成“答完了”。
- **卡片和 Mac 断开时屏幕上看不出来**：卡片断开时清掉了会话表，但旧画面还停在最后的状态。“未连接”和“没有会话”两个整屏画面是实施计划 Task 3 的事。
- **认准自己的卡片**：桥接程序连第一张搜到的卡片。附近有两张卡片时会连错。没在连的那张卡片迟到的连接、断开消息会被忽略，不会打断已经连好的那张，但这一点只按代码检查过，手上只有一张卡片，没有实测。
- **答完了的分钟数最多晚不到 1 分钟**：Mac 发的是取整后的分钟，卡片从收到那一刻起每满 60 秒加 1，两次取整加起来，显示的分钟最多比实际少不到 1 分钟。Mac 只在表变化时发，所以误差不会自己消失，到下一次表变化或重连时归零。
- **沙箱命令要上网的弹窗在终端里拒绝**：这种弹窗只有通知那条记录，没有还连着的 hook，拒绝时桥接程序收不到任何信号。定时核对连续两次看到闲着时去掉这条记录，所以这一行最多约 30 秒后变成“答完了”；这种情况没有单独实测。
- **旧画面只看第一行**：会话表已经按“在跑排在答完了前面”排好，但新的列表画面做好之前，旧画面只显示第一行的状态。
