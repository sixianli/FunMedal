# 卡片固件

本文说明 [firmware/](../firmware/) 里的自制卡片固件（烧在卡片芯片里的程序）第一版：它做什么、怎么编译烧录、怎么测试，以及做的过程中查到的问题。硬件事实（引脚、按键电压）在 [hardware.md](hardware.md)。

固件用 ESP-IDF v5.5.5（乐鑫官方的开发环境）编写。烧上它会覆盖卡片上的原厂固件；原厂固件可以用 `firmware-backup/` 里的完整备份恢复，见“怎么编译和烧录”。

## 对照使命

按 [MISSION.md](../MISSION.md) 的“判断一个需求该不该做”逐条回答：

| 问题 | 回答 |
| --- | --- |
| 1. 补足的是不是电脑端和手机端都做不好的事 | 是。电脑端要走回电脑前看终端；手机端的 Remote Control（用手机远程操作 Mac 上的 Claude Code）要掏手机、解锁、打开 App，才能知道 Claude Code 是不是在等你批准。这一版固件让卡片能显示 5 种状态，是“看一眼就知道状态”的显示部分；还能认出 3 个功能键，是之后“按一个键就处理掉”的输入部分。这一版还没有和 Claude Code 连上（FM-13 做），单独用它还看不到真实状态 |
| 2. 是不是看一眼就懂 | 是。每种状态有自己的背景色、小人动作和一个两到四个字的标签：空闲、干活中、等你批准、完成了、出错了。等你批准时背景一明一暗地闪。（这是当时的画面；2026-10-25 起换成了任务板，见“现在能做什么”） |
| 3. 是不是按一两个键就能完成 | 是。3 个功能键都能分出“按一下”和“按住 0.7 秒以上” |
| 4. 不在电脑前、不想掏手机时是否有用 | 是，卡片自己显示，不用手机。前提是 FM-13 把状态通过蓝牙送到卡片 |

## 现在能做什么

- **显示**：2026-10-25（状态卡片实施计划 Task 3d）起屏幕上是任务板（第一套主题“游戏任务板”）：顶栏，下面一行一个会话，最多 6 行，每行写项目名和状态（等你、出错、在跑、答完了），会话超过 6 个时顶栏右边写“+N”；没连上 Mac 时写“未连接”，连着但没有会话时写“没有会话”。2026-10-25（Task 5）起屏幕上一直有一个角色在动，见“角色”一节。同日（Task 4）起有四套主题：任务板、街机厅、漫画分格、控制塔，按一下中间的键（`up`）换下一套，换到控制塔后再按回到任务板。换主题 1 秒后把主题号写进 NVS（芯片里掉电不丢的小存储区，命名空间 `funmedal`、键 `theme`），所以断电重开还是上次的主题；读不到时是任务板。连按几下只在最后一下的 1 秒后写一次。显示任务每 100 ms 看一次画面，只重画和上次不一样的横条，见“只重画变了的部分”。以前的单个小人画面和它的生成脚本同日删了。
- **按键**：每 10 ms 读一次 GPIO0 的电压，按电压认出是哪个键；连续 3 次读到同一个键才算数，用来滤掉抖动（按键接触瞬间电压来回跳）。按下、按住 0.7 秒、松开各报一次。
- **USB 串口命令**：Mac 上的测试程序通过 USB 串口（卡片用 USB 线连 Mac 时出现的文字通道）读卡片手上的会话表、截取画面、读按键电压，见“USB 串口命令”。
- **蓝牙收状态**：卡片是 BLE（低功耗蓝牙）外设，Mac 上的桥接程序连上后写入会话表，卡片照着表画任务板。服务编号、怎么连和桥接程序见 [bridge.md](bridge.md)（FM-13）。

还不能做的：睡眠省电；读电池电量；原厂的电子名片功能。FM-14 的按键批准、拒绝和 FM-15 的录音做过，2026-10-24 起拿掉了，见 [approval.md](approval.md) 和 [voice.md](voice.md) 开头。

## 怎么编译和烧录

先在终端里启用 ESP-IDF，再编译烧录（卡片要接着 USB）：

```bash
export IDF_TOOLS_PATH=$HOME/esp/.espressif && . $HOME/esp/esp-idf-v5.5.5/export.sh
```

```bash
cd firmware && idf.py -p /dev/cu.usbmodem11301 build flash
```

这样编出来的角色图来自仓库里的默认素材包 `assets/default/`（脚本画的简笔人形）。负责人本机要用自己的素材包 `private-assets/pack/`（不进 git）时，编译时用 CMake 变量 `FUNMEDAL_ASSET_PACK` 指过去（相对路径按仓库根目录算）：

```bash
cd firmware && idf.py -DFUNMEDAL_ASSET_PACK=private-assets/pack -p /dev/cu.usbmodem11301 build flash
```

注意：CMake 会把这个变量记在 `firmware/build/` 的缓存里，之后不带 `-D` 的 `idf.py build` 还是用私有包。编译日志里有一行 `FunMedal character pack: <目录>`，写的就是这次用的包；要换回默认包，就再带一次 `-DFUNMEDAL_ASSET_PACK=assets/default`。`tools/update-prebuilt.sh` 每次都明确指定默认包，所以预编译固件不会带上私有包。

恢复原厂固件：备份是整块 8 MB Flash（存程序和数据的存储芯片）的完整拷贝，从地址 0 整个写回即可。先用 `shasum -a 256 -c` 校验备份没坏。2026-10-17 写回过一次，原厂固件一直启动到 `99-ready`（`notes/hardware.md` “原厂固件完整备份”那一条）。README “恢复原厂固件”也是从地址 0 写回，只是命令名换成 `esptool`，备份文件名换成 `flash.sh` 存的 `factory-full8MB.bin`。那次用的命令是：

```bash
esptool.py --chip esp32c3 -p /dev/cu.usbmodem11301 write_flash 0x0 firmware-backup/trae_card_<id>_fw1.0.3_full8MB_2026-10-16.bin
```

## 编译好的固件文件（OB-15）

使用者不装 ESP-IDF 也能刷固件（负责人 2026-10-17 定，见 [onboarding.md](onboarding.md)）：仓库里放着编译好的固件，只要装 `esptool` 就能刷。

- **放在哪里**：`firmware/prebuilt/`，跟着仓库走（负责人 2026-10-18 选的，每更新一次，仓库历史多约 0.8 MB）。里面有启动程序 `bootloader.bin`、分区表 `partition-table.bin`、程序 `funmedal.bin`，写到哪个地址记在 `flash_args`，SHA-256 记在 `SHA256SUMS`，编译时所在的提交记在 `SOURCE`。
- **怎么生成**：`sh tools/update-prebuilt.sh`，要先运行 ESP-IDF 的 `export.sh`。它只在 `firmware/`、`assets/default/`、`tools/gen_assets.py` 和 `tools/pngio.py` 都没有没提交的改动时才动手（后三个决定了嵌进固件的角色图），用 `idf.py -DFUNMEDAL_ASSET_PACK=<仓库>/assets/default build` 编译（明确指定默认素材包，见“怎么编译和烧录”），按 ESP-IDF 生成的 `build/flash_args` 复制三个文件，再写 `SHA256SUMS` 和 `SOURCE`。脚本放在 `tools/` 而不是 `firmware/`，因为 `firmware/` 下任何文件改了都算固件变了。
- **怎么刷**：仓库根目录的 `flash.sh <端口>`，依次找 `esptool`、`esptool.py`、`.venv/bin/esptool`。先按 `SHA256SUMS` 核对编译好的文件；`firmware-backup/` 里有 `.bin` 时，核对每个都是整块 8 MB、和同名 `.sha256` 文件里的第一个字段对得上，没有时读两遍整块 Flash，两遍一样才存成 `firmware-backup/factory-full8MB.bin` 并写 `.sha256`；最后用 `write_flash` 把三个文件写到 `flash_args` 里的地址。任何一步失败都停下、退出码不是 0，读备份那一步失败或两遍不一样时不留下备份文件。
- **为什么不合成一个文件**：`esptool merge_bin` 能把三个文件合成一个从地址 0 开始的文件，但中间的空隙会填满 0xFF。分区表里 NVS 区（存蓝牙配对的地方）在 0x9000–0xEFFF，正好在分区表（0x8000）和程序（0x10000）之间，合成的文件会把它擦掉，配对就没了。分开写只碰三个文件各自的位置。
- **分区表**（2026-10-25 起，实施计划 Task 3a）：用自己的 `firmware/partitions.csv`，不再用 ESP-IDF 自带的单程序大分区表（程序区只有 1500 KB）。三个区：NVS 区 24 KB 在 0x9000，`phy_init`（存射频校准数据的小区）4 KB 在 0xF000，程序区 `factory` 4 MB 在 0x10000，8 MB Flash 剩下的部分不用。前两个区的位置和大小和原来一样，所以换分区表后配对还在，`flash.sh` 写的三个地址也不变。放大程序区是给后面的字库、角色图和声音留地方：这些素材和程序编在一起，估计合起来约 1.8 MB。`tests/test_flash.py` 的 `test_partition_table` 读编译好的 `partition-table.bin`，核对这三个区的位置和大小，以及程序放得下。
- **怎么保证和源码对得上**：`tests/test_flash.py` 的 `test_prebuilt_is_current` 检查三个文件和 `SHA256SUMS` 一致、`flash_args` 的地址对，并且 `SOURCE` 那个提交之后 `firmware/`（除了 `prebuilt/`）没有改动、也没有新文件。改了固件忘了重新生成，这一项就失败。编译结果不是逐字节可重现的（ESP-IDF 没开 `CONFIG_APP_REPRODUCIBLE_BUILD`），所以测试不重新编译来比对。
- **会不会带出本机信息**：2026-10-18 生成的三个文件里搜不到用户名、`/Users`、仓库目录名和 ESP-IDF 的安装路径：ESP-IDF 默认把源码路径写成 `/IDF/…`。`tests/test_release.py` 发布前还会再查一遍仓库里的所有文件。
- **实测**（2026-10-18）：用 ESP-IDF 自带的 esptool 4.12.0（不经过 `idf.py`）在真卡片上跑 `flash.sh`，已有备份所以只核对没读卡片，三个文件各报一次 `Hash of data verified`，0.8 MB 用了约 3 秒；卡片开机后报 `fw=funmedal-0.1`，配对还在（`sec=encrypted,authenticated,bonded`），桥接程序第一次就连上，版本对得上（`artifacts/ob15-after-20261018-123530/`）。备份、核对、出错停下的各种情况用假的 `esptool` 测（同一个测试文件）。
- **没测的**：Homebrew 的 esptool 5.5.0 和用 `pip` 装的 esptool。esptool 5 把命令和选项改成 `write-flash`、`--flash-mode` 这种带短横线的写法；按乐鑫的[迁移说明](https://docs.espressif.com/projects/esptool/en/latest/esp32c3/migration-guide.html)，`flash.sh` 用的带下划线的旧写法在 v5 里还能用、会打出警告，下一个大版本才删掉。这一点没有在本机用 v5 验证。没有备份时真读两遍 8 MB 的那条路，也只用假的 `esptool` 测过。

## 程序结构

固件里有 4 个并行的任务（FreeRTOS 里同时运行的程序单元，优先级数字越大越先运行）：

| 任务 | 优先级 | 做什么 | 代码 |
| --- | --- | --- | --- |
| 按键 | 6 | 每 10 ms 读一次电压，认出按键，报按键事件；配对画面里的按键也在这里处理（见 [approval.md](approval.md)），其他时候按键只从串口报出来；串口 `key` 命令注入的按键同样在这个任务里处理。栈 4096 字节（FM-14 从 3072 加大，见 approval.md 的“实测结果”第 5 条） | [key_input.c](../firmware/main/key_input.c)、[keys.c](../firmware/main/keys.c)、[key_levels.c](../firmware/main/key_levels.c) |
| 显示 | 5 | 每 100 ms 一步（有人改了画面时立刻多走一步）：算出这一步要显示的画面，只重画和上次不一样的横条；连着 Mac 但 90 秒没收到 ROWS 时主动断开（报 `BLE silent rc=<码>`） | [main.c](../firmware/main/main.c)、[scene.c](../firmware/main/scene.c)、[display.c](../firmware/main/display.c)、[dirty.c](../firmware/main/dirty.c) |
| 串口命令 | 4 | 读 USB 串口上的命令并回复 | [console.c](../firmware/main/console.c) |
| 蓝牙（`nimble_host`） | 21 | ESP-IDF 自带的 NimBLE 蓝牙协议栈建的任务，优先级由它定（`configMAX_PRIORITIES - 4`）；收到 ROWS 写入和配对过程的消息时，都在这个任务里处理并报一行；ROWS 的检查和会话表在 [rows.c](../firmware/main/rows.c) | [ble_link.c](../firmware/main/ble_link.c)、[rows.c](../firmware/main/rows.c) |

- **画面怎么送到屏幕**：一帧 240×320 像素，每像素 2 字节（RGB565，一种红 5 位、绿 6 位、蓝 5 位的颜色格式）。程序每次只算 40 行，放进两块轮流使用的内存，用 DMA（不占 CPU、由硬件自己搬数据的传输方式）经 40 MHz 的 SPI 送给屏幕。
- **字体**：卡片上的字来自三套字库，都在编译固件时生成，生成的文件只在编译目录 `firmware/build/fonts/` 里，不进 git：

  | 字库 | 来源字体 | 大小 | 每个像素 | 字符 | 用途 |
  |---|---|---|---|---|---|
  | `font_text` | Noto Sans SC | 16 像素 | 16 级透明度 | 完整 | 批准内容、项目名、按键提示 |
  | `font_pixel` | Fusion Pixel（BDF 点阵） | 12 像素 | 亮或不亮 | 完整 | 留给以后的像素风格画面，现在的画面还没用到 |
  | `font_large` | 站酷快乐体 | 30 像素 | 16 级透明度 | 只有源代码里的字和 `0123456789/` | 标签、标题、配对数字 |

  “完整”指 ASCII 可见字符、GB2312 一级汉字（最常用的 3755 个汉字）、省略号 `…`、方框 `□`，再加 [firmware/main/](../firmware/main/) 下 `.c` 文件字符串里出现的所有非 ASCII 字符。项目名里有字库没有的字（比如繁体字、日文、表情符号）时画成 `□`；站酷快乐体本身没有 `□`，大字只画源代码里写死的字，用不到它。

  生成过程：[firmware/main/CMakeLists.txt](../firmware/main/CMakeLists.txt) 在编译时运行 [tools/gen_fonts.py](../tools/gen_fonts.py)。它先核对三个字体文件的 SHA-256，对不上就停下；Noto Sans SC 和站酷快乐体用 [tools/gen_font.swift](../tools/gen_font.swift)（调用 Mac 的 CoreText 画字，所以要有 `swiftc`）画成灰度点阵，Fusion Pixel 直接读 BDF 文件里的点阵。三套字库各写成一个二进制文件，用 ESP-IDF 的 `target_add_binary_data` 原样嵌进程序。只要字体文件、生成脚本或 `main/` 下的 `.c` 文件变了，下次编译就重新生成。字体文件本身不进 git，先用 [tools/fetch-fonts.sh](../tools/fetch-fonts.sh) 下载，来源和授权见 [third_party/](../third_party/) 下各目录的 README。

  二进制格式（小端，即低位字节在前）：开头 12 字节是 `FMF1`、行高（1 字节）、每像素位数（1 字节，1 或 4）、2 字节 0、字数（4 字节）；接着每个字 12 字节的索引（Unicode 码位 4 字节、点阵在后面的位置 4 字节、宽度 2 字节、2 字节 0），按码位从小到大排；最后是点阵。4 位点阵每行 `(宽+1)/2` 字节，高 4 位在前；1 位点阵每行 `(宽+7)/8` 字节，最高位在前。开机时 [font.c](../firmware/main/font.c) 逐项检查这三个文件，任何一处不对，串口会输出一行 `FONT damaged`。

  Mac 上以 `[SC-3]` 开头的两条测试（`the body font …`、`the pixel font draws every GB2312 level-one character and a box for any other`）检查两套完整字库能画出每一个一级汉字，字库外的字画成 `□`；以 `[FM-14]` 开头的三条测试检查三套字库里有源代码要画的每一个字。测试还会故意把字库文件截短、改坏开头，确认 `font.c` 不接受坏文件。
- **蓝牙设置**写在 [sdkconfig.defaults](../firmware/sdkconfig.defaults)（ESP-IDF 的编译选项）：只允许 LE Secure Connections 配对（`CONFIG_BT_NIMBLE_SM_LEGACY=n`、`CONFIG_BT_NIMBLE_SM_SC_ONLY=1`），绑定信息存进 NVS（`CONFIG_BT_NIMBLE_NVS_PERSIST=y`），每次传输的上限 512 字节（`CONFIG_BT_NIMBLE_ATT_PREFERRED_MTU=512`），蓝牙任务的栈 6144 字节（`CONFIG_BT_NIMBLE_HOST_TASK_STACK_SIZE=6144`）。为什么要配对加密见 [approval.md](approval.md)。
- **按键电压表**单独放在 [key_levels.c](../firmware/main/key_levels.c)，这样 Mac 上的测试能直接用同一份表。

## USB 串口命令

每条命令一行。卡片对每条命令回一行，开头是 `OK <命令名>` 表示成功，`ERR <命令名>` 表示失败并说明原因；不认识的命令回 `ERR unknown command <命令名>`。Mac 端按命令名对回复，不会把上一条命令迟到的回复当成这一条的。

另外卡片会主动报这些行：开机时 `READY funmedal-0.1`，收到的会话表第一行的状态变了时 `STATE <状态>`（`waiting`、`error`、`working`、`done`，空表是 `idle`），按键时 `KEY <press|long|release> <ok|up|down>`，`adc` 命令期间的 `ADC …`，以及蓝牙的 `BLE rows total=<总数> shown=<行数> fresh=<0 或 1>`（收到一张会话表）、`BLE heartbeat`（收到心跳）、`BLE reject rows`、`BLE reject rows length`（会话表不合规矩或超过 226 字节，被拒绝，规矩见 [bridge.md](bridge.md) 的“卡片怎么收状态”）、`BLE silent rc=<码>`（90 秒没收到会话表或心跳，卡片主动断开）、`BLE connected`、`BLE disconnected reason=<原因码>`、`BLE connect failed status=<码>`，以及 Mac 写来连接协议版本时的 `LINK peer=<Mac 的版本> own=<卡片的版本> match=<1 或 0>`（版本格式不对时是 `BLE reject version`，见 [bridge.md](bridge.md) 的“先核对版本”）。配对相关的行（`BLE sec`、`BLE subscribe`、`PAIR`）见 [approval.md](approval.md) 的“蓝牙协议”；同一处写的 `PROMPT`、`DECISION` 两种行 2026-10-24 随批准一起删了。开机时音频芯片初始化失败会报 `AUDIO unavailable <错误名>`，这时 `tone` 用不了，其他照常。开机时还会报 `GATT layout same` 或 `GATT layout changed subscribers=<数>`，给 Mac 发“功能表变了”的通知时报 `GATT changed sent range=<起>-<止>`，Mac 确认收到时报 `GATT changed acked`，新功能表记好时报 `GATT layout saved`（失败时是 `GATT layout unsaved err=<错误码>`），见下文“换固件后 Mac 还用旧的功能表”。换主题时报 `THEME <主题号>`（0 任务板，1 街机厅，2 漫画分格，3 控制塔），1 秒后写完 NVS 报 `THEME saved <主题号> rc=<结果>`，`rc=ESP_OK` 表示写成功了。

两类输出的发送规则不同：

- **回复**（`OK`、`ERR`、截图）：Mac 刚发了命令，一般在读，所以发送缓冲区满时会等，每次最多等 20 ms，等不到就重试，一行累计等了 2 秒还发不出去才放弃。截图中途放弃时改回 `ERR snap write timed out`。如果连这一行也发不出去，Mac 就收不到这条命令的结尾：前面的行也都没发出去时什么都收不到，发出去了一部分时只收到半张截图。两种情况都记一次 `info` 里的 `replies_dropped`，Mac 端等不到结尾会报超时。
- **主动报的行**：USB 没接电脑时直接丢掉；接着电脑时，等发送权（同一时间只能有一个任务往驱动里写）最多 5 ms、等缓冲区空位最多 5 ms，所以一行最多约 10 ms，还发不出去就整行丢掉，不会只发半行，丢掉的行数记在 `info` 的 `events_dropped` 里。这样没人读串口时，按键任务和显示不会被串口拖住。

`snap` 截的是固件按当前状态重新算出的画面，不是显示任务送给屏幕的那份数据，更不是用摄像头拍屏幕。显示任务有没有真的在画，看 `info` 里的 `draws`、`draw_errors` 和 `shown_tick`。屏幕本身显示得对不对，2026-10-16 由用户看实物确认过一次（见 [hardware.md](hardware.md) 的“结论”）。

## 角色（2026-10-25 起，实施计划 Task 5）

屏幕上一直有一个以负责人女儿为原型的角色在动（PRD Business Rules）。

- **图从哪来**：素材包目录里有 `character/01-lying.png` 到 `10-cheer.png` 十张带透明通道的图。编译固件时 [tools/gen_assets.py](../tools/gen_assets.py) 把每张裁掉透明边，等比缩进五个框：平时用的小图 64 × 74，提醒用的大图 84 × 108（Task 6 才用），以及空地多时用的三档放大图 97 × 112、125 × 145、173 × 200（SC-18）。同一个框里十张图用同一个缩放比例，按最高的那张（歪头）定，所以换姿势时人不会忽大忽小。每个像素存成 RGB565 颜色加 4 位透明度，写成一个二进制文件 `firmware/build/assets/character.bin`，由 `target_add_binary_data` 嵌进固件。图没有透明通道、全不透明、文件损坏或缺一张时，脚本报出文件名并退出，编译失败，不会画出白方块。读写 PNG 用的是仓库里的 [tools/pngio.py](../tools/pngio.py)，因为本机 Python 没有 Pillow（一个常用的图片处理库）。
- **文件格式**：开头 8 字节是 `FMA1`、姿势数、尺寸数和 2 字节保留；后面每张图 8 字节一条索引（宽、高、数据在文件里的位置），按“姿势 0 的五种尺寸、姿势 1 的五种尺寸……”排，每个姿势里依次是小图、大图和三档放大图；再后面是图的数据，先是颜色（每像素 2 字节），再是透明度（两个像素合一个字节）。[character_art.c](../firmware/main/character_art.c) 开机时检查开头、姿势是不是正好 10 个、尺寸数、每张图的宽高是不是不超过它的框（五个框和 `gen_assets.py` 的 `BOXES` 一致），以及每条索引是不是都落在文件里面，有一处不对就一张图都不用，串口报 `ART damaged`。`info` 和 `snap` 里的 `assets=` 是整份数据的指纹，Mac 上的截图比对先核对卡片和宿主渲染器用的是同一个包。
- **怎么动**：[character.c](../firmware/main/character.c) 里一张时间表，动画每 100 ms 走一步，17.8 秒一圈：趴着发呆 5 秒 → 拍桌子 3 下（抬手、拍下各 0.3 秒）→ 歪头，头顶一个“？” 3 秒 → 自言自语，旁边一个“嗯…”的气泡 3 秒 → 打瞌睡，旁边的“zZ”每 0.5 秒往上飘一格，5 秒。问号、气泡和 zZ 用主题自己的两种颜色画。
- **放在哪**：每套主题在 [theme.h](../firmware/main/theme.h) 的 `.home`（平时）和 `.message`（“没有会话”“未连接”这些整屏消息时）两项里写角色框、裁剪范围和问号气泡的位置，数字是负责人 2026-10-25 看 PNG 定的。任务板和街机厅按行排，角色在底栏右下；漫画分格和控制塔按格子排，第 6 格固定是角色的家（漫画是黑边浅黄格，控制塔是写着“CREW”的模块），所以最多显示 5 个会话，顶栏的“+N”按总数减 5 算。负责人原话：“其他主题也一样，我女儿要给足够的空间，如果遮拦到了其他会话，那就不现实那个会话也要给我女儿 留出空间”。整屏消息时，格子型主题的角色站在大消息框的右下角。
- **空地多时变大**（2026-10-25 起，SC-18）：[screen.c](../firmware/main/screen.c) 的 `screen_character_stage` 每画一帧都按当前画面重算角色的位置。先找空地的上边：任务板和街机厅是最后一行会话下面 3 px，整屏消息时是提示字下面 6 px；漫画分格和控制塔把从第一整行空格到第 6 格的格子合成一个大家（`draw_home` 画这一整块，例如 2 个会话时第 3 到第 6 格是一块），空地就是大家里面。再从高 200、145、112 三档里挑最高的一档，右下角和 `.home` / `.message` 里的默认框对齐、上边不越过空地；三档都放不下就是默认 64 × 74。问号气泡和 zZ 跟着框一起挪。会话数一变，下一帧就是新大小。负责人原话见 PRD Business Rules；四档大小和合成大家是负责人看效果图（`private-assets/review/2026-10-25-角色变大-*`）选的。
  - 按现在的排版，112 这一档用不上：任务板和街机厅 4 个会话时 145 已经放得下，5 个会话按负责人的要求必须是默认大小；格子型主题 3、4 个会话时空地上边在第 199 行，112 的框要从第 161 行开始。负责人 2026-10-25 选了留着，以后排版变了、空地变小时会用到，代价是固件多约 0.27 MB。
  - 漫画分格和控制塔没有会话时，提示字在屏幕中间，下面的空地放不下 112，所以她是默认大小，比 1 个会话时（145）小。
  - 街机厅 1、2 个会话时她是 200 高，发呆和打瞌睡的姿势里胳膊会压住左下角 INSERT COIN 的最后一个字母。负责人看过对比图（`private-assets/review/2026-10-25-角色变大-街机厅底栏-三种改法.png`）选了不改。
  - 画得快不快（2026-10-25 在真卡片上实测）：2 个会话、她 200 高时，用 `bench` 从她的头顶画到屏幕底，任务板最慢 23.6 ms、街机厅最慢 33.7 ms；整屏任务板最慢 44.5 ms、街机厅最慢 51.0 ms，都在动画每步 100 ms 以内。测试是 [test_rows.py](../tests/test_rows.py) 的 `test_grown_character_draw_speed`，原始记录在 `artifacts/sc-full-20261025-170137/rows/test_grown_character_draw_speed/`（不进 git）。
- Mac 照旧发 6 行，因为换主题只在卡片上，Mac 不知道现在是哪套。
- **怎么重画**：角色最后画，盖在底栏上面。和角色所占范围上下有重叠的横条，指纹里都混进“角色这一帧”（姿势、问号气泡、zZ 走到第几格）、角色框的位置和尺寸档，所以角色换姿势时只重画它所在的那几块横条。`tests/host/test_screen.c` 的 `test_character_moves` 在四套主题、四种画面下，把每次换姿势前后两帧逐像素比：变了的像素必须在角色框里，或者在自己动画也换了一步的会话格里。

## 画一整屏要多久（2026-10-24 实测）

状态卡片实施计划 Task 0 要先知道现在画一整屏要多久，后面的新画法再和它比。测法是用 USB 串口命令 `timing`：每切一次画面，读一遍最近一次整屏的两个数。卡片当时连着 Mac 的蓝牙。

当时屏幕上还是旧的单个小人画面，表里的 `state` 命令 2026-10-25 已随小人画面删了。

| 画面 | CPU 算像素（毫秒） | 从开始画到屏幕收完（毫秒） |
| --- | --- | --- |
| `state idle` | 22.4 | 34.5 |
| `state working` | 23.2 | 34.0 |
| `state waiting` | 23.9 | 34.5 |
| `state done` | 23.1 | 33.9 |
| `pattern` | 27.7 | 35.3 |

一整屏是 240×320 个点，每点 2 字节，SPI（卡片和屏幕之间的串行数据线）的时钟是 40 MHz，光传数据最少就要约 30.7 毫秒。所以整屏 34 毫秒左右主要卡在传数据上；算像素的 23 毫秒有一大半和传数据同时进行。结论：整屏重画一次大约 35 毫秒，每秒最多重画约 28 次。

## 只重画变了的部分（2026-10-25 起）

状态卡片实施计划 Task 3c 把“每 0.5 秒整屏重画”改成“每 100 ms 看一次，只重画变了的横条”，并写好了画会话列表用的一套公用画图代码。

**怎么知道哪里变了**：每种画面把屏幕从上到下分成几块横条，每块记三样东西：从第几行开始、有多高、一个“内容指纹”。指纹是把这块横条画出来要用到的所有输入（主题号、画面种类、这一格的会话名、状态、显示的“N 分钟前”文字、动画走到第几步）用 FNV-1a（一种很快的散列算法，输入差一点结果就完全不同）算出来的一个 32 位数。显示任务每一步把这次的横条和上次画到屏幕上的横条逐块比：位置、高度、指纹都一样的不画，其余的挨着的合成一段，按 40 行一条送给屏幕。屏幕驱动重建过（`lcd` 命令、`bench` 命令之后）或上次画失败时，整屏重画。代码在 [dirty.c](../firmware/main/dirty.c)、[main.c](../firmware/main/main.c) 的 `display_task`、[display.c](../firmware/main/display.c) 的 `display_draw_spans`。

- 其他画面（配对、版本不配、测试图、整屏填色）只有一块整屏横条，指纹里是画面种类和它自己的内容。以前的小人画面也是这样，每 0.5 秒换帧时整屏重画一次，2026-10-25 删了。
- 任务板分成顶栏（0–23 行）、6 格会话（每格 36 行，从第 24 行起）、底栏（240–319 行，角色在右下）；“未连接”和“没有会话”两种整屏提示把中间 216 行当成一块。所以“在跑”那格的斜纹每走一步、“等你”那格每呼吸一下，只重画自己那格；7 个会话时顶栏右边的“+1”只重画顶栏。街机厅也是这种分法。
- 漫画分格和控制塔是格子型：会话区 2 列 × 3 行，每格 114 × 80 px，格子之间空 6 px，底栏 44 px（第 276–319 行）。第 6 格固定是角色的家，最多显示 5 个会话，见“角色”一节。同一行的两格合成一块横条，指纹由两格各自的指纹合起来算；横条从上一块的下边一直到这一行格子的下边，所以格子上方的 6 px 空隙并进这一块，第三行一直到底栏上边。一格变了，同一行的另一格也跟着重画，换来的是横条之间没有缝、整屏每一行都恰好属于一块。
- 底栏的指纹里有主题自己给的一个“底栏相位”：街机厅的“INSERT COIN”亮 0.6 秒、暗 0.6 秒，只在亮暗切换时重画底栏；其他主题的底栏不动，相位一直是 0。
- 街机厅“出错”那行左右抖，动画每一步都换位置，所以这一行每 100 ms 重画一次（负责人 2026-10-25 定的）。
- “答完了”那格的“N 分钟前”只在文字变了时才重画，比如 135 分钟到 136 分钟都显示“2 小时前”，不重画。

**画图代码**：[draw.c](../firmware/main/draw.c) 是公用的画法：填色、带抗锯齿（边缘半透明、看着不毛糙）的圆角矩形、带边框的圆角块、斜纹、扫描线、贴图、文字（太长时截短加“…”）、半透明叠色块、虚线框、网点、雷达扇形（圆按 16 等分，第几格亮由动画步数定，全用整数算，因为 ESP32-C3 没有浮点运算硬件）。[theme.h](../firmware/main/theme.h) 定义一套主题要提供什么：顶栏、6 格、中间提示区、底栏各在哪里，以及每一块怎么画、动画怎么走。[screen.c](../firmware/main/screen.c) 把卡片手上的会话表变成要显示的画面（没连上 Mac 或还没收到会话表时是“未连接”，总数为 0 时是“没有会话”），按主题画出来，并给每块横条算指纹。第一套主题是 [theme_board.c](../firmware/main/theme_board.c)，照 PRD 效果图 `notes/mockups/2026-10-24-lively.html` 的“游戏任务板”一节画的初稿：等你是黄色块一秒呼吸一次，出错是红色块，在跑是蓝色块上的白色斜纹 0.8 秒流动一圈，答完了是灰色块、右边写多久以前。负责人 2026-10-25 看过 PNG 后定稿，数字不改（Task 3d，见设计规格）。另外三套主题在 [theme_arcade.c](../firmware/main/theme_arcade.c)（街机厅）、[theme_comic.c](../firmware/main/theme_comic.c)（漫画分格）、[theme_tower.c](../firmware/main/theme_tower.c)（控制塔），照效果图 `notes/mockups/2026-10-24-game.html` 的 A、D、E 节画，负责人同日看 PNG 后定稿（Task 4，见设计规格）。主题的先后顺序和“读不到存的主题号时用哪套”写在 `screen.c` 的 `screen_next_theme`、`screen_stored_theme` 里，Mac 上的宿主测试直接测这两个函数。

**在 Mac 上看图**：[tests/host/render_png.c](../tests/host/render_png.c) 用固件同一套画图代码，把一个文本文件描述的画面画成 240×320 的 PNG，同时打印每块横条的位置和指纹。文本文件每行一项：`theme <主题号>`、`tick <动画走到第几步>`、`mode <unlinked|empty|rows>`、`total <会话总数>`、`row <waiting|error|running|done> <分钟或 -> <名字>`。用法：`render_png <字库目录> <画面文件> <输出.png> [输出.rgb]`，字库目录是 `tools/gen_fonts.py --out <目录>` 生成的。`tests/test_firmware_host.py` 跑的时候会把 1、3、6、7 个会话和两种整屏提示各画一张，存进结果目录的 `screens/`。

## 测试音为什么一开始放得很慢

`tone` 第一版每个采样点都调用一次 `sinf`，输入是“第几个点 × 每点转过的角度”，越往后越大，放到 1 秒时已经是几千弧度。ESP32-C3 没有浮点运算硬件，`sinf` 全靠软件算，输入很大时还要先做很慢的取余。实测放 1 秒的音，算波形用了 4.0 秒，写给 I2S（主控和音频芯片之间的数字音频线）只用了 0.027 秒，也就是说声音大部分时间是断的，I2S 发送缓冲区空着时芯片输出的是静音。

现在的做法：开机时算一张 256 个点的正弦表，之后每个点只做一次整数相位累加和一次查表。改完后放 1 秒的音 1.25 秒回复、2 秒的音 2.29 秒回复，多出来的约 0.2 秒是放完后留给芯片把最后一段送完的等待。以后在卡片上实时生成声音，都不要逐点调用 `sinf` 这类软件浮点函数。

## 喇叭的初始化（2026-10-24 起）

按住说话拿掉后，音频的代码只剩 [audio.c](../firmware/main/audio.c)：开机时 `audio_start` 建 I2C 总线（主控用来设置音频芯片寄存器的两根线），只建 I2S 的发送方向，写 ES8311 里放音那条路要用的寄存器，再算好正弦表。以前录音用的 ADC（把麦克风的声音变成数字的部分）寄存器 0x03、0x0e、0x14、0x16、0x17、0x1c 不再写。

I2S 发送方向开机就打开，之后一直开着，没东西放时发 0（`auto_clear_after_cb`），所以给 ES8311 的主时钟一直在走，和以前录音方向一直开着时一样。`tone` 每次只改 0x32 号音量寄存器：放之前设成要的音量，放完等 0.2 秒再改回 0。以前每放一次音都打开、关掉一次发送方向，现在不这样做了。初始化失败时开机报 `AUDIO unavailable <错误名>`，`info` 里 `audio=off`，`tone` 回 `ERR`。

## 串口截图丢数据的问题

**现象**：第一次跑测试时，10 张截图里有 1 张中间少了一段，下一行直接接在半行后面。后来专门测：连续截 30 张，3 张少数据；按字节比对，一次少了 4,215 字节。

**原因（从代码确认）**：ESP-IDF v5.5.5 里 `printf` 经过的串口输出函数 `usbjtag_tx_char_via_driver`（`components/esp_driver_usb_serial_jtag/src/usb_serial_jtag_vfs.c`）在发送缓冲区满时最多等 50 ms，还发不出去就把之后的字符悄悄丢掉，直到缓冲区又有空位。这是为了没人读串口时 `printf` 不会卡住。一张截图有约 31 万字节，只要中途有一次超过 50 ms 发不出去，就会丢数据。少掉的 4,215 字节不是 64 的整数倍（64 字节是一个 USB 数据包），说明丢在逐个字符写入的这一层，不是整包丢。

**排除了的猜测**：

- 不是 Mac 读得慢：故意让 Mac 停 0.5 秒、2 秒再读，截图都完整；一次排队 4 张、8 张截图不读，macOS 先替程序存下了约 240 万字节，卡片照样发得出去。（macOS 能存的量有上限，见下面“没人读串口时”，但这两次都没到上限。）
- 不是重画屏幕引起的：不切换状态、不重画时，12 张里也有 2 张少数据。

**修法**：所有协议输出都不再走 `printf`，而是整行一次交给 USB 串口驱动，规则见“USB 串口命令”里的两类输出。截图写不出去超过 2 秒时回 `ERR snap write timed out`，Mac 端会报错，而不是收到少了一段的数据。整行一次写入还有两个好处：不同任务同时输出时不会把一行插到另一行中间；截图从每张约 2.8 秒变成约 0.5 秒。ESP-IDF 自己的诊断日志仍走 `printf`。

**修好以后**：测试里连续 30 张、单独比对 60 张，共 90 张全部完整。每张截图的 `SNAP END` 行会报出这张截图里单次写入等得最久的毫秒数和超时次数，这 90 张里最久 7 ms，超时 0 次。

**还不知道的**：修之前是什么让 USB 发送停了 50 ms 以上。修之后再也没有出现超过 20 ms 的等待，所以很可能和旧的逐字符写法本身有关，但没有查实。

## 没人读串口时

**问题（代码审核发现，已复现）**：上面的修法刚做完时，主动报的行也用“最多等 2 秒”的规则。卡片用电池、或者接着电脑但没有程序在读串口时，发送缓冲区满了就再也空不出来，于是每报一行 `KEY` 或 `STATE` 都要白等 2 秒。按键任务在这 2 秒里不读电压，期间的按键会丢。

**怎么复现的**：macOS 替程序存的串口数据有上限，这次约 290 万字节。测试先让卡片持续报 `ADC` 行，再一次排队 16 张截图、16 秒不读，存满以后卡片就发不出去了（有截图因此超时，证明确实卡住了）。之后看 `info` 的 `key_gap_ms`：改之前是 2020，也就是按键任务停了约 2 秒；改成上面“主动报的行”的规则后是 10，和正常时一样，同时 `events_dropped` 是 692，说明那段时间报的行被整行丢掉了，没有拖住按键任务。

**同一测试里的另一个现象**：排队的 16 张截图只回来了 13 个结尾（12 张完整，1 张 `ERR snap write timed out`），三次运行都是这样。串口记录里只有 13 个 `SNAP BEGIN`，也没有一行是坏的，所以不是 Mac 收的时候丢了数据。为了查清，固件加了 `replies_dropped`：再跑一次，它从 0 变成 3，正好补上差的 3 张。也就是卡片 16 条命令都执行了，只是有 3 张截图连第一行 `SNAP BEGIN` 和之后的 `ERR` 都在 2 秒内发不出去，于是什么也没回。测试现在要求“回来的结尾数 + `replies_dropped` 增加的数 = 16”，每条命令都要有着落。

**没有测到的**：卡片完全不接电脑（用电池）时的表现。这时 `usb_serial_jtag_is_connected()` 会报告“没连接”，主动报的行直接丢掉；要等 FM-13 有了蓝牙，才能在不接 USB 的情况下读回卡片的状态来验证。屏幕驱动重建失败时退回原设置的那段代码，也没法用串口命令触发，只做了代码检查。

## 换固件后 Mac 还用旧的功能表

GATT 是蓝牙设备对外公布的功能表：卡片有哪些可以读写的项，比如状态、批准请求、录音。2026-10-17 早上，卡片换上带语音的固件后，桥接程序 3 分钟里连了 358 次，每次都只找到旧固件的 3 项（状态、批准请求、回答），找不到语音的 3 项，于是断开重连。记录在 `artifacts/fm13-gatt-cache-before-20261017-101731/bridge.jsonl`。

**原因**：macOS 把配对过的蓝牙设备的功能表记在本机，下次连接直接用记下的，不再问设备。设备的功能表变了，要由设备发一个 `Service Changed` 通知（蓝牙标准里“我的功能表变了，请重新读”的通知），Mac 收到后才会重新读。卡片用的 NimBLE 蓝牙库带这个通知，但旧固件从没发过。

**改法**：卡片开机时把自己的功能表算成一个指纹，和上次存在 NVS（芯片上存设置的一小块存储）里的比较。指纹包括每一项的编号（UUID，蓝牙用来认项的标识）、读写方式和句柄（handle，Mac 读写某一项时用的位置编号），也包括 NimBLE 自带的 GAP 服务（设备名一类的基本信息）和 GATT 服务（放 `Service Changed` 的那一组）的编号和起始句柄，但不包括这两组里面各项的读写方式：比如只改设备名能不能写，指纹不变，不会发通知。

- 一样：报 `GATT layout same`，什么也不发。
- 不一样或者没存过：调用 NimBLE 的 `ble_svc_gatt_changed` 发通知，报 `GATT layout changed subscribers=<数>`。`subscribers` 是订阅了这个通知、还等着收的已配对设备数，本机的 Mac 是 1。

新指纹不是马上存，而是等每个订阅的设备都确认收到才存，存好时报 `GATT layout saved`，存失败时报 `GATT layout unsaved err=<错误码>`。没有设备订阅时马上存。如果卡片还和一台再也不连的设备配对着、它也订阅过这个通知，新指纹就一直存不下，卡片每次开机都会再发一次；按代码推断，连着的 Mac 只是每次多读一遍功能表，没有实测过。通知真的发出去时报 `GATT changed sent range=<起>-<止>`，范围是 `0001-ffff`，意思是“全部重新读”；Mac 确认时报 `GATT changed acked`。

**为什么要等确认再存**：第一版改法是开机发现变了就马上存新指纹，以为 NimBLE 会替没连着的 Mac 记下“还欠一个通知”。读 ESP-IDF v5.5.5 的代码后发现，这个“还欠”的标记只在内存里：`ble_store_config_persist_cccds`（`ble_store_nvs.c`）只在订阅记录的条数变了时才写 NVS，标记变了不写。所以 Mac 确认之前卡片重启一次，标记就没了，新指纹却已经存下，下次开机报 `same`，Mac 永远收不到通知。用旧固件复现过：忘掉指纹后连着重启两次，第二次就报 `same`，测试等不到 `GATT changed sent`（`artifacts/fm13-unconfirmed-before-20261017-110935/`）。

**为什么 GATT 服务要排在最前**：Mac 记的订阅是按句柄记的。各组服务按注册的先后分句柄，旧固件先注册 GAP 服务，GAP 服务里多一项，后面所有句柄都往后挪，`Service Changed` 自己的句柄也跟着挪。Mac 订阅的还是旧位置，卡片找不到这个订阅，于是 `subscribers=0`，通知发不出去。实验在 `artifacts/fm13-handle-shift-20261017-111512/`，都是用 ESP-IDF 的 `CONFIG_BT_NIMBLE_SVC_GAP_CAR_SUPP=y`（让 GAP 服务多一项“中心设备地址解析”）把句柄挪动。重跑：把 `firmware/` 复制一份、在副本里打开这个配置，再运行 `.venv/bin/python artifacts/fm13-handle-shift-20261017-111512/experiment.py <阶段名> <副本目录>`，结果会写进脚本所在目录下以阶段名命名的子目录。各阶段的结果：

| 阶段 | 固件 | 结果 |
| --- | --- | --- |
| b | 旧固件 | 报 `same`，不发通知；桥接程序 32 次写入全部出错，卡片状态没变 |
| c、c2 | 指纹不含句柄 | 报 `same`；忘掉指纹再重启，报 `changed subscribers=0`，还是发不出去 |
| e | GATT 服务排在最前，指纹含句柄 | 报 `changed subscribers=1`，发出并收到确认；桥接程序 2 次写入都成功，卡片变成空闲 |
| f | 同 e，换回平常的配置 | 同 e |

现在 `ble_link_start` 先注册 GATT 服务、再注册 GAP 服务，`Service Changed` 的句柄固定是 3，不管 GAP 服务或我们自己的服务怎么变。`info` 里的 `gatt_changed` 报这个句柄。这次挪动本身也让 Mac 记的订阅失效，所以 2026-10-17 用户决定固定这个句柄（任务目标记录 `goal.md` 的 G33），并重新配对了一次（`artifacts/fm13-repair-20261017-112321/`）。

**结果**：

- [test_bridge.py](../tests/test_bridge.py) 的 `test_layout_change_announced_once`：先用 `ble layout forget` 忘掉指纹，再在 Mac 确认前连着重启两次，两次都要报 `changed` 且订阅数至少 1；然后启动桥接程序，要求报 `GATT changed sent range=0001-ffff`、`GATT changed acked`、`GATT layout saved`；第三次重启要报 `same`，之后不再发通知，桥接程序连上。记录在 `artifacts/fm13-unconfirmed-after-20261017-112018/`。
- 同一文件的 `test_changed_notice_position_fixed`：要求 `info` 的 `gatt_changed` 是 3。改之前 `info` 里没有这一项（`artifacts/fm13-fixed-position-before-20261017-112244/`），改之后通过（`artifacts/fm13-fixed-position-after-20261017-112501/`）。

**以后改功能表**：只要固件里的功能表变了，指纹就会变，不用另外做什么。如果某次换固件后开机报 `subscribers=0`，说明 Mac 没订阅这个通知或者订阅的位置不对，只能在卡片上运行 `ble unpair`、在 Mac 的“系统设置 → 蓝牙”里忽略卡片，再照 README 第 4 步重新配对。用本项目 2026-10-17 之前的固件配对过的 Mac，换到现在的固件时都要这样重新配对一次。
